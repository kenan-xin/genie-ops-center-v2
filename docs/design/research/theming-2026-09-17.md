# Customer theming research, 2026-09-17

Question (findings M1): what may a tenant administrator change about the look of their own deployment, where does it show, and how do we stop a color choice that makes text unreadable? Stack: React 19, Tailwind v4, shadcn/ui on Base UI.

## How shadcn/ui theming works

1. Every color is a CSS custom property on `:root` (light) and `.dark` (dark): `--background`, `--foreground`, `--primary`, `--secondary`, `--muted`, `--accent`, `--destructive`, `--border`, `--input`, `--ring`, five chart colors, and an eight-token sidebar group (`--sidebar`, `--sidebar-primary`, `--sidebar-accent`, and their foregrounds).
2. Every surface token pairs with a `-foreground` token, so text always has a declared partner.
3. Components read the variables through Tailwind utilities (`bg-primary`, `text-primary-foreground`).
4. One `--radius` drives a derived scale.
5. A runtime theme is a set of variable values on `<html>` or a wrapper; nothing in a component changes.
6. `shadcn/create` picks a base neutral, a radius, and a font and emits the CSS block. It is a developer tool, not an admin tool.

Source: https://ui.shadcn.com/docs/theming

## What real products let a customer administrator set

| Product | What can be set | Where it shows | Restrictions | Contrast rule |
|---|---|---|---|---|
| Slack | 8 hex colors for the sidebar | Sidebar only, per user | No validation | None |
| Auth0 Universal Login | Primary, page background, logo, and email logo and text | Sign-in page and emails only; the product shell is untouched | Per organization | None built in |
| Zendesk | Brand color, brand text color, text color, logo, favicon | Agent nav bar and help center | Named tokens only, no palette | None built in |
| Atlassian Jira and Confluence | Named pickers: link, header, menu; logo, favicon | Whole product shell | Predefined inputs, light and dark each checked | WCAG AA enforced by the token system, 4.5:1 text and 3:1 UI |
| Microsoft 365 (SharePoint, Teams) | One seed color; the system derives a 16-token palette | Whole shell | Theme Designer validates every pair | Refuses to publish a palette with a failing pair |
| Retool | Primary color, logo, custom CSS | Whole app | Custom CSS bypasses any guard | None |
| Grafana, Backstage | Theme objects for primary, secondary, nav, typography; logo | Whole portal | Separate light and dark objects | None |

The pattern: identity products (Auth0, Okta) brand the sign-in page and emails and leave the product shell neutral. Collaboration suites (Microsoft 365, Atlassian) brand the whole shell but derive the palette from one seed and validate every pair before saving. Products that expose many free colors (Slack, Retool) accept unreadable results as the administrator's problem.

## Contrast safeguards, simplest to most robust

1. Computed foreground: white or near-black text chosen by contrast against the surface. Zero input, always readable. Already in this design (`foregroundFor`).
2. Lightness clamp: derive every shade from the seed by holding hue and stepping lightness, and clamp the ends so hover, active, and text tones stay inside a contrast band. Already in this design for dark mode (`darkVariant`).
3. Tonal palette from one seed (Material Design 3): about thirty tones derived together, so surface and content pairs pass by construction. https://m3.material.io/styles/color/overview
4. WCAG AA check with save blocking: compute every pair after a change; a failing pair blocks Publish. Microsoft Theme Designer does this. Already in this design (Publish blocked while a pair fails).
5. Nearest passing color: offer the closest hue-preserving color that passes instead of only refusing. Already in this design (Fix button).
6. APCA instead of WCAG 2.1 ratios: better for thin text and dark surfaces; Radix Colors and Carbon target it. https://www.radix-ui.com/colors

## Three options for Genie Ops Center

Option 1, minimal: one brand color. The administrator sets primary only; the app derives primary foreground, hover, and the dark variant. It reaches the sign-in page, emails, solution monograms, and small accents in the shell (active nav row, focus ring, primary button). Sidebar and page chrome stay neutral gray. Secondary and accent leave Branding and the platform. Lowest risk; the existing contrast check and Fix already cover it. This is the Auth0 and Zendesk shape plus shell accents.

Option 2, moderate: one seed, derived palette, branded shell accents. Same single input, but the app derives a tonal palette and writes the shadcn primary and sidebar-primary variables per request, so the active nav, buttons, pills, and focus ring take the tenant color in light and dark. Chrome stays neutral. Contrast is safe by construction because every tone is derived. Needs the CSS variable layer and a change to `tokens.md` and `shell/spec.md`. This is the Microsoft 365 shape with one seed.

Option 3, full: several named pickers (brand, sidebar background, sidebar text, page accent), light and dark sets, a validator on every change with nearest-passing suggestions and an explicit acknowledgement before Publish. Most brand fidelity, most work, most support load. This is the Atlassian shape.

Recommendation: Option 1 now, with the variable layer named as the upgrade path to Option 2. The shell already fixes blue for actions, one input keeps the Branding page and the contrast rules that exist, and a later move to Option 2 changes only which variables the tenant primary fills, not the Branding page.
