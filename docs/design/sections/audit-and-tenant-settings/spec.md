# Audit and Tenant Settings Specification

## Overview
Four admin portal screens. Audit log is the read-only, filterable reader of the tenant's append-only audit events for administrators holding `core:audit:read`. Tenant settings is the page where an administrator holding `core:settings:manage` owns the non-branding tenant settings (onboarding mode, local accounts, session idle timeout) and the per-tenant configuration of each installed module, rendered from the module's declared schema. It is a section navigator with a search over every setting, not one long page of cards, because a tenant with a dozen modules cannot scan one column. Modules, behind the same key, lists every module compiled into the image with a category picker, a read-only view of who reaches it, and one of two enable controls: a switch for an ordinary module, or a Review and enable button for a module that returned to the deployment after it was removed (DEC-50, `architecture/module-removal.md`). Categories, behind the same key, manages the core `category` table that groups solutions and modules alike in the navigation tree (DEC-51). Designed mobile first: the phone layout is the base and desktop adds columns.

## User Flows
- Administrator opens Audit log and sees the newest events first. Each row shows when, who, what action, on which target, and a one-line summary.
- Administrator narrows the list with the toolbar: free-text search over summary and target, then a Filters button holding actor (people plus System), action (grouped by module prefix), target type, and a date range with presets Today, Last 7 days, Last 30 days, and Custom (from and to). The button carries the count of active filters. Active filters show as removable chips with a Clear all. A range with no events shows an empty state with Clear filters.
- Administrator clicks a row. A detail sheet opens on the right (full-height on phones) with the actor (monogram, name, email, or System), the action as a pill, the exact time in the viewer's time zone with the relative time, the target with an Open link only when the event carries a path the server supplied and authorized for this reader (the module contract's resolver returns a label and an optional path; the screen never builds a route from the target type, so a target that still exists but resolves to a label alone carries a No link pill instead), the summary, the metadata as labeled key-value rows, and a Show JSON disclosure with the raw event. The event id is shown in mono for support tickets.
- Administrator scrolls to the end of the loaded page and presses Load more. The footer reads Showing n of total; Load more is shown only while more events can load. Events are never edited or deleted; there is no action on a row other than opening it.
- Administrator sees a removed person's earlier events under an anonymized name, and a target that no longer exists shown without a link and labeled Removed.
- Administrator opens Tenant settings and sees a section navigator, not a long page of cards. The navigator holds two groups: Tenant (Sign-in & accounts, Sessions) and Modules (one row per installed module that declares a configuration schema, in module order). One section's form sits beside it. A module without a schema has no row, so Solutions, which declares no tenant configuration, is absent.
- Administrator types in Search all settings, above the navigator and the form. The search reads the name, the description, and the keywords of every setting they may change, and it tolerates one typo from four letters, so "timout" finds Idle timeout and "remidners" finds Renewal reminders. It reads no saved value and no secret.
- Administrator reads a result as the setting name with its section breadcrumb, for example "Idle timeout, Tenant › Sessions". Choosing one opens that section, puts the focus in the field, and rings it for a moment.
- Administrator searches for something that is not a setting and reads one card that says nothing matches, and what the search does and does not read.
- Administrator opens the section of an installed module that is switched off. Its fields stay editable through this authorized core path, so the tenant can be prepared before the module is enabled, and one amber note says that saving changes settings only and never switches the module on. Saving also never skips the reintroduction review of a module that returned after a removal. Switching it on happens on the Modules page, which the note links to. A module excluded from the image has no section at all, and neither does a module that declares no schema.
- Administrator saves and the server refuses. The section keeps the typed values, says "Not saved" with the reason, and offers Retry. Nothing reads as saved.
- Administrator leaves a section with unsaved changes, by choosing another section, by following a search result, or by going back on a phone. A confirm step names the section and offers Discard. The navigator marks an unsaved section with a dot.
- Administrator on a phone sees the search field and the section list first, chooses a section, and works on it as its own screen with an All settings control back to the list.
- Administrator changes onboarding mode between Invite only and Just-in-time in the Onboarding card. The card explains each mode in one line. Save enables when dirty; Discard restores the saved value.
- Administrator turns local accounts on or off. When the tenant realm is brokered only, the switch is disabled with a note to ask the Genie operator. When turning it on, the card states that Add person will also create the account in the realm and send a set-password email.
- Administrator changes the session idle timeout in minutes (5 to 480, default 15). A note states that the change applies to new sessions and to existing sessions on their next activity.
- Administrator edits a module's section rendered from the schema: string, number, boolean switch, enum select, and string list fields, each with a title and description, and constraints from the schema (min, max, pattern, max length, item limit). Validation messages appear under the field on blur and block Save. The section saves on its own.
- Every card footer shows who last changed it and when. Saving shows a 4-second toast with a manual close and writes an audit event. Discarding a dirty card needs no confirm; nothing on either screen is destructive.
- Administrator opens Modules and sees every module compiled into the image, enabled or not, in image order. Each row shows the display name, the module id in mono, a one-line description, the Enabled switch, the Category picker, and Access: the groups and people who hold a role carrying the module's `<id>:use` key, read from role assignments.
- Administrator switches an ordinary module on. It saves at once. Switching a module off opens a confirm dialog: "Switch off Contracts?" with the consequence "Members lose Contracts from their navigation until it is switched on again. Its data stays." The switch writes `tenant_module.enabled` through the same core procedure as `genie-ops module enable|disable`. This is the flow for every module whose server activation state is `ready`, switched off or not.
- Administrator sees a module that returned to this deployment after it was removed. Its row reads Review needed and carries no switch, because enabling it restores the access assignments the tenant kept (`architecture/module-removal.md`). The state comes from the server's activation verdict. It is never read from `enabled === false`, which an ordinary switched-off module also carries.
- Administrator presses Review and enable and reads a panel with four parts: why the module is off, the retained configuration, the retained access, and what enabling does not bring back.
- Administrator reads the retained access as one row per kept assignment: the group or the person, the role, what the assignment covers, the member count for a group, and whether it restores. An assignment that will not restore is marked Will not restore with the reason, for example a group archived since removal, or a permission the module no longer declares. The list only reads. Change assignments in Access opens `/admin/access?module=<id>&level=use`, and the panel carries no permission editor of its own (`DEC-39`).
- Administrator reads the retained configuration in the review itself, as one read-only row per field: the field title and the value the module will run with. The decision is made here, so the values are not one navigation away. Editing is not offered in the panel; Open <Module> settings opens the module's own section. A value saved there appears in the review the next time it is opened, and saving settings never switches the module on.
- Administrator follows a retained assignment into Access, removes it there, and returns to the review. The list is one assignment shorter and the restore count drops, because both screens read the same assignments. Nothing about that removal enables the module.
- **Open decisions** for this section: the server activation read model, and review freshness and stale-confirmation recovery. See `../../decisions-open-2026-09-19.md`, rows B2 and B3. The preview proves the journey with synthetic state; it proves no server contract.
- **Accepted in v2 on 2026-09-19:** the category assignment boundary and the settings discovery and authorization boundary, both in `docs/architecture/module-contract.md`. Rows B4 and B5 are closed and this section follows them.
- Administrator finishes the review and enables the module. It is an ordinary module from then on: switching it off leaves the ordinary switch and the ordinary confirm, and switching it on again is one step. The reintroduction review is asked for once, after the module returns, never again because it is switched off. Enablement alone cannot carry this, since an ordinary switched-off module and one still awaiting its review both read `enabled: false`; the server's activation verdict carries it.
- Access reads the same module state this screen writes, so a module enabled here stops reading as switched off on the Access screens.
- Administrator reads a row marked Does not restore now. The assignment is kept, not deleted. It grants nothing in this activation for the stated reason, and a later membership, status, scope, permission, or entitlement change is judged again by ordinary authorization. The screen never says that an assignment can never matter again.
- Administrator whose module has invalid required configuration reads a one-line refusal above the list, and the field at fault marked in the list with what to do about it, for example "Register name is required. Set it in the settings section, then reopen this review." The confirmation cannot be ticked. Saving in the settings section writes `tenant_module.config` and never enables the module, so the administrator returns to Modules to enable it.
- Administrator ticks one confirmation that names the outcome: "I read the retained access. Enabling Asset register restores the 3 assignments marked Restores, and nothing else." Enable is refused until the box is ticked and the configuration is valid. One line states that the server runs these checks for this screen and for `genie-ops module enable`, and that the box records the decision rather than enforcing it.
- Administrator closes the panel with Cancel, the close button, Escape, or the scrim. Nothing is written, the module stays off, and reopening starts with the box unticked.
- Administrator whose activation the server refuses reads "Not enabled", the reason the server gave, and that the module is still switched off and nothing was restored. The ticked review is kept and the button becomes Retry enabling. No success toast appears.
- Administrator whose activation succeeds sees the panel close, a toast "<Module> is on. Written to the audit log.", and the row become an ordinary module with a switch. Revoked credentials are not revived, cancelled work does not resume, and stopped schedules stay stopped. The panel stated each of those before the decision.
- Administrator picks a category for a module from the core categories or No category. It saves at once and writes `tenant_module.category_id`. The picker shows for every module with at least one static workspace entry, and the solutions hub is such an entry (DEC-49), so the Solutions row has one; setting it moves the hub entry under that heading. A module with no static workspace entry shows no picker (DEC-50). A solution's own place in the tree comes from its `solution_category` row, which the solutions admin owns.
- Administrator reads Access and follows Manage in Access to `/admin/access?module=<id>&level=use`, which opens the Grants screen with the module and the level already chosen. Nothing on the Modules page writes an assignment (`DEC-39`). A module nobody holds shows "No one holds Contracts user yet" with the same link.
- Administrator opens Categories and sees the core categories in order, each with its modules count, and a fixed Other row at the bottom with the count of ungrouped modules. The count comes from `tenant_module.category_id` only; there is no solutions count, because `solution_category` is a module table that core does not read (DEC-51).
- Administrator reads one line under the title: a category groups what people already see, and it never grants access. Who can open a module or a solution is set in Access.
- Administrator scrolls to Assign items and files one item at a time. Each row carries the name, one scan fact, a type pill (Module or Solution), and a category dropdown that holds No category and every category. One category per item.
- Administrator searches the rows, narrows them to modules only or solutions only, or ticks Uncategorized only. The filters are a convenience and are never required.
- Administrator files the Solutions module row and sees that only the hub entry moves. The row says so, and the nine solutions keep the category each one carries.
- Administrator picks a category and the row reports the save, then the page toast repeats it. A refused write leaves the dropdown at the value the server still holds, says "Not saved" with the reason, and offers Retry. No refused write ever reads as a save.
- Administrator who holds `core:settings:manage` and not `solutions:admin` can file a module and cannot file a solution. The solution rows are read-only and name the key they need. The page itself stays open, because module placement is core's own write.
- Administrator opens Assign items while a module is switched off. The module's own row stays, because `tenant_module.category_id` is core's column. The records of that module are not listed, because a switched-off module answers nothing, and what it stored is kept.
- Administrator deletes a category. Its modules and its solutions become ungrouped, nothing is deleted, and no permission changes. A category id that no longer exists reads as no category everywhere (R-91).
- Administrator creates a category from the input at the top, renames one inline by clicking its name, and reorders by drag or with the up and down arrows (keyboard and phones).
- Administrator deletes a category, in use or not. A confirm dialog names the module count and mentions solutions without a number: "Delete Finance?" with "1 module becomes ungrouped, and solutions in this category lose their heading. Nothing is deleted with it." Its members move to Other; a module treats the missing id as no category and core never touches a module table.
- Every change on Modules and Categories shows a 4-second toast "Saved. Written to the audit log." and writes an audit event.
- Validation, one message per field kind (DEC-28): string "is required" or "Keep … to N characters"; number "must be at least" or "at most"; a required boolean that is unset "Choose on or off"; a required enum left at Select… "Choose a value"; string list per-entry pattern message. A stored value that fails the schema shows its message on load; other fields show theirs on blur.

## UI Requirements
- Audit log page: title Audit log with the description "Who did what, when, on which record. Events are kept for the tenant's lifetime and never edited." Toolbar on one row at every width: the search field with its help icon, then a Filters button carrying the count of active filters. The panel stacks actor, action, target type, and date range, with two date inputs under the range when Custom (empty until the administrator picks dates), and a Clear filters control at its foot. Active filter chips sit on their own row below the toolbar with a Clear all. Four selects standing in the row crushed the search field, which is why they moved behind the button (`design-system/tokens.md`, Filter disclosure).
- Audit table (desktop): When (relative, with the exact time on hover), Actor (monogram and name, or a System mark), Action (gray pill with the `module:verb` key in mono), Target (type as small text, label), Summary (clamped to one line). Newest first. Rows are clickable; the whole row is the target. On phones each event is a card: first line actor and relative time, second line action pill, third line summary.
- Footer: Showing n of total in small text and a Load more secondary button. No pagination controls, no export.
- Detail sheet: 480px on desktop, full-height sheet on phones. Header with the action pill and close button. Body sections: Actor, When, Target, Summary, Details (key-value rows, values in mono when they look like ids or keys), then a Show JSON disclosure with a scrollable pre block (gray-50 with a hairline border in light, gray-900 in dark). Footer: Event id in mono with a Copy button.
- Tenant settings page: title Tenant settings with the description "Sign-in, sessions, and the settings each module exposes for this tenant. Branding has its own page." One row at the top holds the Search all settings field and a What is searched help disclosure. Below it, a 232px navigator on the left and the selected section on the right from `md`; one column under it.
- Settings navigator: a gray-50 panel, sticky on desktop, with an uppercase group label (Tenant, Modules) over each list. A row is a `rounded-lg` button at the control height carrying the section name, an unsaved dot when the section has unsaved changes, a Sample pill for a scale fixture, a Disabled pill for a switched-off module, and a chevron under `md`. The selected row is the active navigation treatment: white fill, hairline ring, blue text. One line under the groups says that a module appears only when it declares settings, and that switching a module on or off happens on the Modules page.
- Settings navigator type: the group caption is uppercase `text-xs` semibold at `tracking-wider` in gray-600, gray-400 in dark. A section name is `font-medium` and the selected one `font-semibold`, so a state pill never outreads the name. A truncated name carries its full text in `title`. The closing line sits under a hairline rule, which is the only rule in the panel. Full rules in `../../design-system/tokens.md`, Section navigator.
- Settings section: one card. Title, one-line description, then the fields, then a footer with Last changed by name and time on the left and Discard and Save on the right. Save is disabled until the section is dirty and while any field is invalid. Each section saves on its own; no page-level save exists.
- Save failure: the footer grows one line above the buttons, "Not saved", the reason the server gave, "Your changes are still here", and a Retry control that sends the same values again. The success toast never appears for a refused save.
- Search results replace the section pane on desktop and the whole page under `md`. Each row is the setting name over its breadcrumb, `Tenant › Sessions` or `Modules › Contracts`, with a chevron. The empty state names the query and states that saved values and secrets are never searched.
- A switched-off module's section carries the warning note of the design system with the module name, one sentence that its settings stay editable for preparation, and one that saving never switches it on, with a link to Modules.
- A design fixture module carries a Sample pill in the navigator and one line in its section saying it exists to show the navigator at scale and is not part of the product.
- Unsaved work: changing section, following a search result, and the phone Back control all pass through the confirm dialog, which names the section and offers Discard. Nothing here is destructive, so the dialog is the plain one, not the danger tone.
- Onboarding card: radio list with Invite only ("Only people an administrator adds can sign in.") and Just-in-time ("Anyone your identity provider signs in is added on first sign-in.").
- Local accounts card: switch with the label Allow local accounts, the note under it, and the disabled state with the brokered-only note.
- Sessions card: number input Idle timeout in minutes with a unit suffix and the range note.
- Module configuration sections: the module name as the title and its description; fields from the schema in declared order. String is a text input with a counter when max length is set. Number is a numeric input with min and max shown in the description. Boolean is a switch. Enum is a select with the option labels. String list is a list of rows with a remove button and an Add row action, disabled at the item limit, and per-row validation against the pattern.
- Modules page: title Modules with the description "Every module compiled into this deployment. Switch one on or off, place it in a category, and see who reaches it." Desktop table columns: Module (display name, id in mono, description clamped to one line; a gray Off pill for an ordinary switched-off module, an amber Review needed pill for one awaiting its reintroduction review), Enabled, Category (select of the core categories in order plus No category), Access (one line naming up to two holders, groups first with their member counts, then a `+n` count for the rest; the whole line links to that module's Access screen and the remaining names sit in its `title`; "No one yet" when nobody holds it). On phones each module is a card: name row with the enable control, then Category, then Access, same content. The switch-off confirm is the confirm dialog from `design-system/tokens.md` with the danger tone; Cancel is focused.
- Modules page Enabled column: an ordinary module shows the switch. A module whose server activation state is `review-required` shows a secondary Review and enable button and no switch at all, because an actionable switch would imply a one-step enable that the policy forbids. The column is 150px wide so the button holds one line, and the table's minimum width is 900px.
- Module review panel: the shared slide-over, 480px on desktop and a full-height sheet on phones, titled "Review <Module> before enabling" with the module id in mono under it. Focus moves to the title on open. Escape, the scrim, the close button, and Cancel all cancel and write nothing. Body, in order: the amber warning note saying the module returned on its date and stays off whatever it was before; Retained configuration, which states the server's verdict, then lists the settings the tenant kept as read-only label and value rows in the module's declared field order, then the line that the list only reads and that saving settings never switches a module on, then the link to the module's settings section. The server renders each value, because core holds no copy of the module's schema here: an enum reads as its label, an unset field as Not set, and a secret as a placeholder. A field the server refused is marked in the list with its own message saying how to recover; Retained access, whose heading counts how many of the kept assignments restore, one row per assignment with a Restores or Does not restore now pill, the recipient name as a link into Access with that recipient and this module already chosen, a line of role, scope and member count, the reason under an invalid one, the line saying that the list only reads and that a kept assignment which does not restore now is not deleted and not barred for good, and the link to Access; What enabling does not bring back, a short list of plain facts about revoked credentials, cancelled work, stopped schedules and deleted assignments.
- Module review footer: the confirmation checkbox naming the module and the count of assignments that restore, one line stating that the server runs these checks for this screen and for `genie-ops module enable` and that the box records the decision rather than enforcing it, then Cancel and the primary Enable <Module> button. The button is disabled until the box is ticked and the configuration is valid, and it shows the shared loading state while the server answers.
- Module review failure: a red `role="alert"` line above the footer controls reading "Not enabled", the reason the server gave, that the module is still switched off and nothing was restored, and that the review is still there. The confirmation stays ticked, the primary button reads Retry enabling, and no success toast appears.
- Categories page: title Categories with the description "Headings in everyone's navigation. Solutions and modules share them." New category input with Add at the top (Add moves to the sticky bottom bar under 768px, DEC-25). One list: drag handle, up and down arrow buttons, name with inline rename on click, one modules count pill, and a delete button that is always enabled. Other is a fixed, non-editable footer row with its modules count. On phones the count and delete wrap to a second line under the name.
- Assign items card, under the category list on the Categories page: the heading Assign items, a count pill of what is uncategorized, one line of instruction, then a search field, a type select (All types, Modules only, Solutions only), and an Uncategorized only checkbox. Desktop columns are Item, Type, Category; under 768px each row is a card with the same three parts. A row's dropdown holds No category first, then every category in order.
- Assign items rows: one row per module with at least one static workspace entry, and one row per record an enabled module contributes. A module with no workspace entry is absent, and the footer says why. A module row that owns records carries the line "Moves this entry only. Its N solutions keep the category each one carries", so the hub and its solutions are never confused.
- Assign items states: saving shows a spinner and the word Saving; success shows a check, the line "Saved. Written to the audit log", and the page toast; failure shows an alert line with the reason, the value the row still holds, and a Retry control that sends the same value again; a row the viewer may not write is disabled and names the key it needs; an empty result reads "No item matches", and a tenant with nothing to file reads that a module with a workspace entry, and every solution, appear here.
- The write behind a row depends on the row. A module row writes `tenant_module.category_id`, which is core's own column, behind `core:settings:manage`. A record row belongs to a module, so the module contributes the row and performs the write behind its own key, for example `solutions:admin`. Core reads and writes no module table (DEC-51). The interface is accepted: a module declares an optional `listAssignable` and a per-record assign or clear contribution, and core dispatches through the compiled registry without importing module internals (`docs/architecture/module-contract.md`, Category assignment boundary, accepted 2026-09-19).
- Each write targets one record and one core category id, or no category. Core validates the category, and the owning module rechecks the caller, the tenant, its own availability and the record at write time, then audits the change. Moving several rows at once is not one transaction across modules: each row reports its own outcome and a failed row can be retried on its own. Placement never grants access.
- A switched-off compiled module keeps the record placement it already has and contributes no editable record rows, so its records leave the list while it is off. Its own module row stays, because that placement is core's column. A module excluded from the image contributes nothing at all. The category summary counts stay whole-module counts.
- Modules page Category column: a module with no static workspace entry shows no picker and reads "No workspace entry, so nothing to place" (R-84).
- Contextual help (design system, Help disclosure): one collapsed button per screen. Tenant settings carries What is searched beside the search field. Modules carries What a module is here as an icon beside its search field, and it says that the list is the deployed image, that switching a module off keeps its data, and that the Access column only reads. Categories carries What the counts mean under its guidance line, and it says that the count counts modules only, that deleting a category deletes nothing else, and that Other is fixed. Audit log carries Why a row can look incomplete as an icon beside its search field, and it says that an event is never edited, that a target links only while the record exists and its module returns a path, and that an erased person reads as an anonymized name.
- Permission gating: Audit log requires `core:audit:read`; Tenant settings, Modules, and Categories require `core:settings:manage`. That key is the baseline for reading, writing, navigating and searching settings, and a section's optional additional permission narrows it further: it is an AND restriction, never a substitute. Holding a module's own administration key alone opens no central settings section, and unauthorized section metadata never reaches the browser. The components trust the host for this: a person without the permission does not see the nav item and the route is not mounted; the screens do not render a denied state. A direct link and a save are checked again on the server.
- Phone: Categories moves Add to the shell bottom bar; the other screens have no page-level primary action (each settings section saves on its own; the audit log is read-only; Modules saves per control). Tenant settings on a phone is a list screen and a detail screen, never a squeezed desktop sidebar.
- All screens in the admin chrome. Tokens per `../../design-system/tokens.md`.
- Out of scope: CSV export, SIEM push, retention settings, editing or deleting events, a Solutions settings section (the module has no tenant configuration, DEC-30), a settings search that reads saved values or secrets, a global save, role assignment on the Modules page or inside the review panel (access changes happen on the Access screen, `DEC-39`), adding a module that is not compiled into the image (the image is the commercial boundary, DEC-33), API keys, integrations, and any operator setting.
- Out of scope, module lifecycle: uninstalling a module, permanently deleting its data, and the controlled removal an operator runs before an image can drop a module. Those are separate authorized operator workflows in `architecture/module-removal.md`, not tenant administrator screens. Until controlled removal is implemented and its lifecycle tests pass, an upgrade that omits a previously installed module stays prohibited, so this section designs the return of a module and never its departure.
- Backend contract, flagged rather than invented: the durable representation of the review, the tables that hold the activation verdict and the retained-grant validity, and how the shared procedure records review evidence for both the screen and the command line. The design names the shape it needs and no more. See `product/amendments-modules-2026-09-19.md`.
