# Audit and Tenant Settings Specification

## Overview
Four admin portal screens. Audit log is the read-only, filterable reader of the tenant's append-only audit events for administrators holding `core:audit:read`. Tenant settings is the page where an administrator holding `core:settings:manage` owns the non-branding tenant settings (onboarding mode, local accounts, session idle timeout) and the per-tenant configuration of each entitled module, rendered from the module's declared schema. Modules, behind the same key, lists every module compiled into the image with an enabled switch, a category picker, and a read-only view of who reaches it (DEC-50). Categories, behind the same key, manages the core `category` table that groups solutions and modules alike in the navigation tree (DEC-51). Designed mobile first: the phone layout is the base and desktop adds columns.

## User Flows
- Administrator opens Audit log and sees the newest events first. Each row shows when, who, what action, on which target, and a one-line summary.
- Administrator narrows the list with the filter bar: free-text search over summary and target, actor (people plus System), action (grouped by module prefix), target type, and a date range with presets Today, Last 7 days, Last 30 days, and Custom (from and to). Active filters show as removable chips with a Clear all. A range with no events shows an empty state with Clear filters.
- Administrator clicks a row. A detail sheet opens on the right (full-height on phones) with the actor (monogram, name, email, or System), the action as a pill, the exact time in the viewer's time zone with the relative time, the target with an Open link when the target still exists and the owning module's record-type resolver returns a path (the module contract's resolver returns a label and an optional path; core links only when a path is present, so a module that resolves labels only shows no link), the summary, the metadata as labeled key-value rows, and a Show JSON disclosure with the raw event. The event id is shown in mono for support tickets.
- Administrator scrolls to the end of the loaded page and presses Load more. The footer reads Showing n of total; Load more is shown only while more events can load. Events are never edited or deleted; there is no action on a row other than opening it.
- Administrator sees a removed person's earlier events under an anonymized name, and a target that no longer exists shown without a link and labeled Removed.
- Administrator opens Tenant settings and sees cards: Onboarding, Local accounts, Sessions, then one card per entitled module that declares a configuration schema, in module order. A module without a schema shows no card.
- Administrator changes onboarding mode between Invite only and Just-in-time in the Onboarding card. The card explains each mode in one line. Save enables when dirty; Discard restores the saved value.
- Administrator turns local accounts on or off. When the tenant realm is brokered only, the switch is disabled with a note to ask the Genie operator. When turning it on, the card states that Add person will also create the account in the realm and send a set-password email.
- Administrator changes the session idle timeout in minutes (5 to 480, default 15). A note states that the change applies to new sessions and to existing sessions on their next activity.
- Administrator edits a module configuration card rendered from the schema: string, number, boolean switch, enum select, and string list fields, each with a title and description, and constraints from the schema (min, max, pattern, max length, item limit). Validation messages appear under the field on blur and block Save. The card saves on its own.
- Every card footer shows who last changed it and when. Saving shows a 4-second toast with a manual close and writes an audit event. Discarding a dirty card needs no confirm; nothing on either screen is destructive.
- Administrator opens Modules and sees every module compiled into the image, enabled or not, in image order. Each row shows the display name, the module id in mono, a one-line description, the Enabled switch, the Category picker, and Access: the groups and people who hold a role carrying the module's `<id>:use` key, read from role assignments.
- Administrator switches a module on. It saves at once. Switching a module off opens a confirm dialog: "Switch off Contracts?" with the consequence "Members lose Contracts from their navigation until it is switched on again. Its data stays." The switch writes `tenant_module.enabled` through the same core procedure as `genie-ops module enable|disable`.
- Administrator picks a category for a module from the core categories or No category. It saves at once and writes `tenant_module.category_id`. Solutions has no category of its own; its entries carry theirs.
- Administrator reads Access and follows Manage in Roles to `/admin/roles` to change who holds the module's user role. Nothing on the Modules page assigns a role (DEC-39). A module nobody holds shows "No one holds Contracts user yet" with the same link.
- Administrator opens Categories and sees the core categories in order, each with its solution count and module count, and a fixed Other row at the bottom with the counts of ungrouped solutions and modules.
- Administrator creates a category from the input at the top, renames one inline by clicking its name, and reorders by drag or with the up and down arrows (keyboard and phones).
- Administrator deletes a category, in use or not. A confirm dialog names the counts: "Delete Finance?" with "2 solutions and 1 module become ungrouped. Nothing is deleted with it." Its members move to Other; a module treats the missing id as no category and core never touches a module table.
- Every change on Modules and Categories shows a 4-second toast "Saved. Written to the audit log." and writes an audit event.
- Validation, one message per field kind (DEC-28): string "is required" or "Keep … to N characters"; number "must be at least" or "at most"; a required boolean that is unset "Choose on or off"; a required enum left at Select… "Choose a value"; string list per-entry pattern message. A stored value that fails the schema shows its message on load; other fields show theirs on blur.

## UI Requirements
- Audit log page: title Audit log with the description "Who did what, when, on which record. Events are kept for the tenant's lifetime and never edited." Filter bar on one row on desktop, wrapping on phones: search field, actor select, action select, target type select, date range select with two date inputs when Custom (empty until the administrator picks dates). Active filter chips below the bar.
- Audit table (desktop): When (relative, with the exact time on hover), Actor (monogram and name, or a System mark), Action (gray pill with the `module:verb` key in mono), Target (type as small text, label), Summary (clamped to one line). Newest first. Rows are clickable; the whole row is the target. On phones each event is a card: first line actor and relative time, second line action pill, third line summary.
- Footer: Showing n of total in small text and a Load more secondary button. No pagination controls, no export.
- Detail sheet: 480px on desktop, full-height sheet on phones. Header with the action pill and close button. Body sections: Actor, When, Target, Summary, Details (key-value rows, values in mono when they look like ids or keys), then a Show JSON disclosure with a scrollable pre block (gray-50 with a hairline border in light, gray-900 in dark). Footer: Event id in mono with a Copy button.
- Tenant settings page: title Tenant settings with the description "Sign-in, sessions, and the settings each module exposes for this tenant. Branding has its own page." Cards in a single column of at most 720px. Each card: title, one-line description, fields, footer row with Last changed by name and time on the left and Discard and Save on the right. Save is disabled until dirty and while any field is invalid.
- Onboarding card: radio list with Invite only ("Only people an administrator adds can sign in.") and Just-in-time ("Anyone your identity provider signs in is added on first sign-in.").
- Local accounts card: switch with the label Allow local accounts, the note under it, and the disabled state with the brokered-only note.
- Sessions card: number input Idle timeout in minutes with a unit suffix and the range note.
- Module configuration cards: the module name as the title and its description; fields from the schema in declared order. String is a text input with a counter when max length is set. Number is a numeric input with min and max shown in the description. Boolean is a switch. Enum is a select with the option labels. String list is a list of rows with a remove button and an Add row action, disabled at the item limit, and per-row validation against the pattern.
- Modules page: title Modules with the description "Every module compiled into this deployment. Switch one on or off, place it in a category, and see who reaches it." Desktop table columns: Module (display name, id in mono, description clamped to one line; an Off pill when disabled), Enabled (switch), Category (select of the core categories in order plus No category), Access (a count line such as "2 groups, 1 person via Contracts user", then one gray chip per group with its member count and one per person, then the Manage in Roles link; the empty state text and the same link when nobody holds it). On phones each module is a card: name row with the switch, then Category, then Access, same content. The switch-off confirm is the confirm dialog from `design-system/tokens.md` with the danger tone; Cancel is focused.
- Categories page: title Categories with the description "Headings in everyone's navigation. Solutions and modules share them." New category input with Add at the top (Add moves to the sticky bottom bar under 768px, DEC-25). One list: drag handle, up and down arrow buttons, name with inline rename on click, a solutions count pill and a modules count pill, and a delete button that is always enabled. Other is a fixed, non-editable footer row with its counts. On phones the counts and delete wrap to a second line under the name.
- Permission gating: Audit log requires `core:audit:read`; Tenant settings, Modules, and Categories require `core:settings:manage`. The components trust the host for this: a person without the permission does not see the nav item and the route is not mounted; the screens do not render a denied state.
- Phone: Categories moves Add to the shell bottom bar; the other screens have no page-level primary action (each settings card saves on its own; the audit log is read-only; Modules saves per control).
- All screens in the admin chrome. Tokens per `../../design-system/tokens.md`.
- Out of scope: CSV export, SIEM push, retention settings, editing or deleting events, a Solutions settings card (the module has no tenant configuration, DEC-30), role assignment on the Modules page (access changes happen on the Roles screen, DEC-39), adding a module that is not compiled into the image (the image is the commercial boundary, DEC-33), API keys, integrations, and any operator setting.
