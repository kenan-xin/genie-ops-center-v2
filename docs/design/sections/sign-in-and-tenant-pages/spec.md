# Sign-in and Tenant Pages Specification

Owner decision 2026-09-27 (`../../decisions-open-2026-09-19.md`, row B6): an existing local account keeps the same sign-in route after local-account creation is switched off. While any local account exists, the sign-in page keeps "Sign in with email and password", and the realm keeps its password form and reset flow (Specification 02 R-51a).

Redesign 2026-10-27 (owner, approved direction D2): the sign-in page is one centered stack with no card. The captures in this folder that show a card predate the redesign and are replaced when the redesign is built.

## Overview
The pages a person sees before a session exists. Members sign in through the tenant's Keycloak realm, so the Genie sign-in page is a branded page with a "Sign in with SSO" button, a "Sign in with email and password" button when the realm allows local accounts, and no email field. A hidden break-glass administrator door at `/admin/login` uses a password and an authenticator-app code. One deployment serves one customer at one `PUBLIC_URL`; the app never inspects the hostname, so there is no tenant resolution and no not-found or suspended page. One standalone page covers the gap before setup: a not-set-up page shown on every route until `genie-ops setup` completes. A limited break-glass session, which still has to change its password or enroll an authenticator, has no page of its own: every other page sends it back to `/admin/login`, which opens at the next unmet step. All of these render without the app shell.

## User Flows
- Member opens the deployment's `PUBLIC_URL`, sees the branded sign-in page, presses "Sign in with SSO", and is sent to the tenant realm with `kc_idp_hint=company-login`. On return a session exists and they land on the Solutions hub.
- Member of a tenant with a system-use notice sees the notice above the buttons. If the tenant requires acknowledgement, the buttons stay disabled until the checkbox is ticked.
- Member who signed out sees the sign-in page with a "You are signed out" banner. In client-only mode the signed-out banner reads "You are signed out of {productName}. Your company sign-in stays active." Member whose session expired sees the same page with a banner that names the tenant's idle timeout, for example "Your session expired after 15 minutes of inactivity".
- A person whose company account is not registered (in `invite` mode, or in `jit` mode with no mapped group in their `groups` claim) returns from the realm to the sign-in page with a warning banner: not registered, ask your administrator. A disabled member returns with an access-disabled warning banner. Neither creates a session.
- Member of a tenant whose realm allows local accounts (Specification 02 R-17c) sees a second button, "Sign in with email and password", under "Sign in with SSO". It starts the same sign-in without the hint, so the realm shows its password form. The password form and its "Forgot your password?" reset link are Keycloak pages, not designed here. With local accounts off, only the SSO button shows.
- Enrolled break-glass administrator opens `/admin/login`, enters email and password, then enters the six-digit authenticator code on a second step. On success they land in the admin portal.
- Break-glass administrator on first sign-in (not enrolled) enters email and password, then a forced password-change step, then an authenticator enrollment step (QR code, manual key, confirm with one code from the app), then the admin portal. There is no code step: there is no authenticator to ask a code from yet. Enrollment is also required after an operator rotates the account, which clears the authenticator.
- Break-glass administrator enters a wrong password or code and sees an inline error on the same step. A non-admin credential is refused with a neutral message and no session.
- Break-glass sign-in is rate limited per deployment and every refusal is an audit event. Past the limit, the credentials step shows a neutral notice "Too many sign-in attempts. Try again in N minutes." with its inputs disabled and no retry button.
- Break-glass administrator whose session is limited (must change password, or authenticator not enrolled) opens any other page and is sent back to `/admin/login`, which shows the next unmet step (Specification 02 R-65). There is no limited-session page.
- Visitor opens any route of a deployment where `genie-ops setup` has not completed and sees the not-set-up page with the progress of the setup steps the running image knows (seven once Section 2 is deployed). The health endpoint reports degraded. Nothing on the page is actionable by a visitor.

## UI Requirements
- Centered stack, no card (redesign 2026-10-27, mockup direction D2): one column of about 320px in the middle of the page, light and dark, phone and desktop. Top to bottom: the tenant logo mark alone (or the letter tile fallback), with no wordmark that repeats the heading; the heading "Sign in to Genie Ops Center" in Plus Jakarta Sans; the notice when there is one; the sign-in buttons. Each button fills the stack width at the 40px default control height, with no arrow icon and no explanation line under it. "Sign in with SSO" is the primary button and always shows. "Sign in with email and password" is the outline button and shows only when the realm allows local accounts (Specification 02 R-17c). No password field sits on this page, because the password form is the realm's own page. The page has no "Welcome" line, no "Genie" wordmark over the product name, and no product name in a footer, because each repeats the heading.
- Sign-in page reads tenant branding: logo for the current theme, background image or color, support contact, terms and privacy links. When Branding sets the links or the support contact, they sit in one small muted line under the stack. No hostname is shown anywhere.
- System-use notice renders as a bordered block in the stack above the buttons, in body type, with an optional checkbox "I acknowledge these conditions." that gates the buttons.
- Status notices sit between the heading and the buttons at the stack width, built with the shared `Alert` in a tone per cause. Signed out and session expired use the info tone with the `Info` icon and `role="status"`, for example "You were signed out after 15 minutes of inactivity. Sign in again." Not registered and access disabled use the warning tone with `role="alert"`, because the realm authenticated the person and Genie refused them. Never one gray box with `role="alert"` for every cause.
- The break-glass sign-in at `/admin/login` uses the same stack, width, logo mark and buttons, with its own fields and no card. The show-password toggle is an eye button inside the password field (an Input Group item). The "Step n of m" counter is muted text in the body font, not monospace.
- Break-glass steps show a blue-tinted Administrator pill and the muted "Step n of m" counter above the fields, m being the number of steps the account still has to pass: two for an enrolled account (credentials, code), three for a first sign-in (credentials, change password, enroll). Step one: email and password with a show-password toggle; when rate limited, a neutral gray notice sits above the fields, the fields and the button are disabled, and there is no retry control. Code step, enrolled accounts only: six one-digit code boxes with a "Use a different account" link back to step one. Forced change: current, new, and confirm password with a strength meter that applies the shared rule (14 characters, three of four character classes, not equal to the email); the fourth rule, not the provisioning password, is checked only on submit and shown neutral ("Checked when you save") with no check mark. The meter is gray until the rule is met and emerald once it is. Enrollment: a QR code, the manual key in mono groups of four with a copy button, and one six-digit code entered in six boxes; the account is enrolled only after one valid code. The change-password and enrollment steps both carry the note "Until you finish setup, every other page brings you back here.", because the open step can be the password change. A "Member sign-in" link under the stack returns to the member sign-in page.
- The six code boxes are one labeled group, used on the code step and on the enrollment step alike. A `fieldset` with a visible `legend` names it ("Authentication code"), each box carries its own `aria-label` ("Digit 1 of 6"), and the group sets `inputmode="numeric"` with `autocomplete="one-time-code"` so a phone offers the code from its messages. Typing a digit advances one box, Backspace on an empty box steps back, the arrow keys move without changing a value, and pasting a six-digit string fills every box and moves focus to the last one. A wrong code clears every box, returns focus to the first, and announces the error through the form-level `role="alert"` block, so the message is not lost to a screen reader.
- Inline errors sit under the field or as a compact error block above the action. Copy never says whether an email exists.
- Not-set-up page: standalone, neutral gray, not tenant-branded beyond the product name because branding may not be seeded yet. Heading "This deployment is not set up yet", one line "An operator must finish `genie-ops setup` before anyone can sign in.", then a progress list of the `setup_step` rows in `../../../architecture/data-shape.md` (`migrations`, `seed`, `realm`, `clients`, `roles`, `admin_seed`, `break_glass`, in run order; the identity provider is not a step, `DEC-36`) each marked pending, done, or failed, with a detail line under a failed step. No button. A support line appears only when tenant branding provides a support contact.
- Designed mobile first; phone layout is the base and the desktop layout adds columns. On phones the stack keeps its width and at least 16px margins on each side.
- All pages support light and dark themes and follow the tenant default theme. Focus order and contrast meet WCAG 2.1 AA.
- Out of scope: member password fields inside Genie, self sign-up, and the Keycloak-hosted screens themselves (the realm sign-in form for local-account tenants and its reset-credentials page).
