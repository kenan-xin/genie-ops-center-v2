# Sign-in and Tenant Pages Specification

**Open decision:** how an existing local account still reaches sign-in and password reset once local-account creation is switched off. Turning the setting off keeps the accounts that already exist (R-51a), and this design does not yet name the route they use. See `../../decisions-open-2026-09-19.md`, row B6. It is proposed, not accepted.

## Overview
The pages a person sees before a session exists. Members sign in through the tenant's Keycloak realm, so the Genie sign-in page is a branded page with one company-account button and no email field. A hidden break-glass administrator door at `/admin/login` uses a password and an authenticator-app code. One deployment serves one customer at one `PUBLIC_URL`; the app never inspects the hostname, so there is no tenant resolution and no not-found or suspended page. Two standalone pages cover the gaps around a session: a not-set-up page shown on every route until `genie-ops setup` completes, and a limited-session page shown while the break-glass account still has to change its password or enroll an authenticator. All of these render without the app shell.

## User Flows
- Member opens the deployment's `PUBLIC_URL`, sees the branded sign-in page, presses "Continue with your company account", and is sent to the tenant realm. On return a session exists and they land on the Solutions hub.
- Member of a tenant with a system-use notice sees the notice above the button. If the tenant requires acknowledgement, the button stays disabled until the checkbox is ticked.
- Member who signed out sees the sign-in page with a "You are signed out" banner. In client-only mode the signed-out banner reads "You are signed out of {productName}. Your company sign-in stays active." Member whose session expired sees the same page with a banner that names the tenant's idle timeout, for example "Your session expired after 15 minutes of inactivity".
- A person whose company account is not registered (in `invite` mode, or in `jit` mode with no mapped group in their `groups` claim) returns from the realm to the sign-in page with a warning banner: not registered, ask your administrator. A disabled member returns with an access-disabled warning banner. Neither creates a session.
- Member of a local-accounts tenant sees the same page with the button labeled "Continue to sign in" and a "Forgot your password?" link that opens the realm's reset flow. The password form itself is a Keycloak page, not designed here.
- Enrolled break-glass administrator opens `/admin/login`, enters email and password, then enters the six-digit authenticator code on a second card. On success they land in the admin portal.
- Break-glass administrator on first sign-in (not enrolled) enters email and password, then a forced password-change card, then an authenticator enrollment card (QR code, manual key, confirm with one code from the app), then the admin portal. There is no code step: there is no authenticator to ask a code from yet. Enrollment is also required after an operator rotates the account, which clears the authenticator.
- Break-glass administrator enters a wrong password or code and sees an inline error on the same card. A non-admin credential is refused with a neutral message and no session.
- Break-glass sign-in is rate limited per deployment and every refusal is an audit event. Past the limit, the credentials card shows a neutral notice "Too many sign-in attempts. Try again in N minutes." with its inputs disabled and no retry button.
- Break-glass administrator whose session is limited (must change password, or authenticator not enrolled) opens any other page and is refused with the limited-session page. Its one button returns them to the break-glass flow at the first unmet step.
- Visitor opens any route of a deployment where `genie-ops setup` has not completed and sees the not-set-up page with the progress of the setup steps the running image knows (seven once Section 2 is deployed). The health endpoint reports degraded. Nothing on the page is actionable by a visitor.

## UI Requirements
- Centered auth card: tenant logo (or the letter tile fallback) and company name above the card, Plus Jakarta Sans card title, one primary action. The card width and padding are fixed tokens.
- Sign-in page reads tenant branding: logo for the current theme, background image or color, welcome text, support contact, terms and privacy links. Links and support contact sit in a footer under the card, with the product name (from tenant branding) as a small gray label beneath them on every auth card. No hostname is shown anywhere.
- System-use notice renders as a bordered block inside the card above the button, in body type, with an optional checkbox "I acknowledge these conditions." that gates the button.
- Status banners appear at the top of the card. Signed out and session expired use the neutral blue tint. Not registered and access disabled use the amber warning tint, because the realm authenticated the person and Genie refused them.
- Break-glass card shows a blue-tinted Administrator pill and a mono "Step n of m" counter in the card head, m being the number of steps the account still has to pass: two for an enrolled account (credentials, code), three for a first sign-in (credentials, change password, enroll). Step one: email and password with a show-password toggle; when rate limited, a neutral gray notice sits above the fields, the fields and the button are disabled, and there is no retry control. Code step, enrolled accounts only: six one-digit code boxes with a "Use a different account" link back to step one. Forced change: current, new, and confirm password with a strength meter that applies the shared rule (14 characters, three of four character classes, not equal to the email); the fourth rule, not the provisioning password, is checked only on submit and shown neutral ("Checked when you save") with no check mark. The meter is gray until the rule is met and emerald once it is. Enrollment: a QR code, the manual key in mono groups of four with a copy button, and one six-digit code entered in six boxes; the account is enrolled only after one valid code. The change-password and enrollment cards both carry the note "Until enrollment is complete, every other page brings you back here." A "Member sign-in" link under the card returns to the member sign-in page.
- The six code boxes are one labeled group, used on the code step and on the enrollment card alike. A `fieldset` with a visible `legend` names it ("Authentication code"), each box carries its own `aria-label` ("Digit 1 of 6"), and the group sets `inputmode="numeric"` with `autocomplete="one-time-code"` so a phone offers the code from its messages. Typing a digit advances one box, Backspace on an empty box steps back, the arrow keys move without changing a value, and pasting a six-digit string fills every box and moves focus to the last one. A wrong code clears every box, returns focus to the first, and announces the error through the form-level `role="alert"` block, so the message is not lost to a screen reader.
- Inline errors sit under the field or as a compact error block above the action. Copy never says whether an email exists.
- Not-set-up page: standalone, neutral gray, not tenant-branded beyond the product name because branding may not be seeded yet. Heading "This deployment is not set up yet", one line "An operator must finish `genie-ops setup` before anyone can sign in.", then a progress list of the `setup_step` rows in `../../../architecture/data-shape.md` (`migrations`, `seed`, `realm`, `clients`, `roles`, `admin_seed`, `break_glass`, in run order; the identity provider is not a step, `DEC-36`) each marked pending, done, or failed, with a detail line under a failed step. No button. A support line appears only when tenant branding provides a support contact.
- Limited-session page: standalone, product name, heading "Finish setting up your account", one line explaining that other pages open after the password change and the authenticator enrollment, a two-item checklist showing which of the two is done, and one primary button "Continue setup" that returns to the break-glass flow.
- Designed mobile first; phone layout is the base and the desktop layout adds columns. The card fills the width on phones with 16px margins.
- All pages support light and dark themes and follow the tenant default theme. Focus order and contrast meet WCAG 2.1 AA.
- Out of scope: member password fields inside Genie, self sign-up, and the Keycloak-hosted screens themselves (the realm sign-in form for local-account tenants and its reset-credentials page).
