# Access Specification

## Overview
Two admin portal screens behind `core:roles:manage`. Grants is the one place that writes `role_assignment`. Its everyday flow is three steps: pick a group, move rows between Catalog and Granted, save. Overview is read-only and answers who reaches what, through which role and group. Everything that is not an ordinary grant, which is administration levels, one record of a module that owns records, and custom roles, sits behind one Advanced access action. Access belongs to core administration, so it stays reachable when the solutions module is switched off. Roles keeps role definitions only, and a module's own screens link here instead of editing access themselves (`DEC-39`, one writer). Designed mobile first: the phone layout is the base and desktop adds columns.

## User Flows
- Administrator opens Access, picks a group from the searchable dropdown, and sees the catalogue at once. No module, level, or role is chosen first, because every row means the same thing: this group can use it.
- Administrator ticks three rows in Catalog, presses Add 3, and saves. Each row writes one assignment of a predefined role: a solution row writes the solutions user role scoped to that solution, a module row writes that module's own user role with no scope, because the module owns no records to scope to. A module row grants use, never administration, and neither row needs a role to be assigned first.
- Administrator never sees the solutions module itself beside its solutions. Access to every solution is the separate broader-access choice, so a row and a whole module are never interchangeable.
- Administrator searches the Catalog side, presses Add all shown, and adds exactly the rows the search left. It never adds a row the filter hides and never covers a record added later.
- Administrator narrows a long catalogue with the Show filter, All items, Solutions only, or Modules only. The filter is a convenience and is never required.
- Administrator needs access to everything of one kind, so they tick a row in Broader access, for example "Every solution, now and in the future". The row names how many records it covers today and says that it also covers later ones. It is never mixed with the catalogue rows.
- Administrator grants to one person instead of a group. The People segment switches the dropdown, and the empty state says that a person is the exception. The Groups empty state says that a group is the normal path, because the identity provider keeps it current.
- Administrator opens the screen for a tenant whose Solutions module is switched off. Every solution row and the "Every solution" choice are blocked, on every path: the row checkbox, select all, Add all shown, and the same three steps inside Advanced access. Each blocked row reads "Inactive, the Solutions module is off" and carries the reason.
- Administrator removes a grant while its module is switched off. Removal stays available on the Granted side, so a kept assignment can always be taken away.
- Administrator switches the module on again. The kept assignments apply once more, subject to the solution's own status and the other access rules. Nothing is rewritten, because nothing was deleted.
- The same rules hold for every other module: a switched-off module takes no new grant, keeps what it has, and shows why.
- Administrator sees a line under the catalogue naming the grants this screen cannot show, for example an administration role or one contract, with a link into Advanced access. Nothing is hidden.
- Administrator opens Advanced access for administration levels, for one record of a module that owns records, for core administration, for the audit role, or for a custom role at a scope. It writes through the same procedure and keeps the same safeguards.
- Administrator tries to remove core administration from the last recipient that still carries it, or from themselves, in Advanced access. The control is disabled with the reason, as on People and Groups. The rule counts the people who would still be able to administer the tenant, not the grant rows: only an active person counts, a pending or disabled person counts for nobody, a path through an archived group counts for nobody, and two paths to one person are still one person. It counts by role, not by the level a screen happened to show. "Assign a role directly" records the same Tenant administrator role without a level, so a rule keyed on the level would miss every grant made that way and could read a tenant with one administrator as having none.
- Administrator saves a batch the screen believed was allowed, because somebody else removed the other administrator while this page was open. The server refuses, the screen states the reason where the pending count sits, and every unsaved change stays on the screen. The screen check explains the rule first; the server holds it.
- Administrator changes the recipient with unsaved changes. A confirm step names the count and offers Discard.
- Administrator opens Overview, chooses "By group or person" or "By module or record", then picks one subject. Nothing loads before that. Results are searchable and paged, and each row names the holder, what it reaches, the role, how it arrives, and who added it.
- Administrator reads a row that says "also through Clinical Operations": that same person reaches that record twice, so removing one grant leaves the other. Two different groups holding the same record are not each other's alternate path, and the page never says so. The page explains this under the table and links to the audit log for what changed and when.
- Administrator opens How access works beside the catalogue heading and reads five sentences: roles define what somebody can do, people receive access directly and through their groups, the grants combine within their scopes, removing one does not remove another, and a disabled account or module still blocks access. The callout is collapsed until it is asked for.
- Administrator picks a person whose group already carries a solution. The row stays on the Catalog side and reads "Also through Claims Review", so the side a row sits on never means that the person has no access. One line under the list says that this screen writes the direct assignments only.
- Administrator removes a grant that another group still supplies. The pending bar names what stays, and Save asks first and lists every path that remains. No message says that access was revoked.
- Administrator removes the "Every solution" grant while named rows stay granted. The same confirmation names how many rows stay.
- Administrator arrives from Modules, People, Groups, Roles, or one solution through a prefilled link and lands on the same dropdown with the recipient chosen.
- Administrator arrives from one solution's configure sheet, which carries the module, the level, and that solution. The screen names the solution above the recipient control and keeps naming it after a recipient is chosen, because choosing who receives access is the step this screen asks for and finding the solution again is not. A solution is a catalogue row, so both lists open narrowed to it, and Show everything widens them. A record of a module that owns records is not a catalogue row, so the line says that Advanced access edits it and links there, already set to that module and level. This screen stays the one writer either way.

## UI Requirements
- Renders in the admin portal chrome under one page title, Access, with two tabs: Grants and Overview. The tab is the route, so a link can open either one.
- Grants toolbar, one row at the control height: the label Grant to, a segmented control with Groups and People, the recipient dropdown, then Advanced access at the far right. Switching the segment clears the recipient, and the empty state names the choice. There is no sentence offering the person path: the segment is the offer.
- The recipient dropdown holds one line, an icon, the name, and one short fact such as "17 members" or the email address. It opens a panel with a search field and the list of that segment, each row with its icon, name, and detail. Escape and a click outside close it.
- Before a recipient is chosen the page shows one card that says a group is the normal path and why. No catalogue loads.
- Help disclosure (design system, Help disclosure): one collapsed button, How access works, beside the catalogue heading on Grants and at the end of the toolbar on Overview. It opens on click, on tap, and on Enter or Space, and Escape closes it. It explains additive access and scopes, and it never carries a consequence that the confirmation must carry.
- A catalogue row that the recipient already reaches another way carries a third line, "Also through <group>", and one line under the list says that this screen writes the assignments made to the recipient directly. A person reads these rows, because a group receives nothing through another group.
- Removal consequences: while a removal waits to be saved, the pending bar names the first path that stays. Save then opens the confirm dialog, which lists every path that stays and never says that access was revoked. A removal with no other path saves at once.
- Catalogue card: the heading "Access assignments", one line that names the recipient and says that Granted means an assignment exists and not that the resource works today, and the Show filter with All items, Solutions only, Modules only. Then the transfer list.
- Catalogue rows: one row per solution of the solutions module, and one row per other module whose use grant needs no record. The solutions module itself is never a row. Each row carries a type pill, Solution or Module, its one-line detail, and a Pending pill while its change is unsaved.
- A row whose module is switched off reads "Inactive, the <module> module is off" in its detail line, carries an Inactive pill, and cannot be ticked on the Catalog side. Select all and Add all shown skip it. On the Granted side it stays fully selectable, so the assignment can be removed. The same block applies to its broader-access row and to the same module inside Advanced access, where an amber line states it.
- Transfer list (design system: Transfer list, two-pane form): Catalog on the left, Granted on the right, each with a count, a select-all box, a search field, a quick action for everything shown ("Add all shown", "Remove all shown"), and one button that moves the ticked rows ("Add 3", "Remove 2").
- A line under the transfer list names every grant of this recipient that the catalogue cannot show, with its role and record, and links to Advanced access.
- Broader access card, under the catalogue, collapsed by default, because the everyday grant is a named row. Its header is the toggle: a chevron, the title, one line that says the grant also covers records added later, the count of what is on, and a What is this? help disclosure that explains a grant with no scope. The card opens itself when the chosen recipient already holds one of these grants, so nothing granted is ever hidden, and a press then pins it open or closed until the recipient changes.
- Broader access rows: one checkbox row per module that owns records, reading "Every <record>, now and in the future", with the count it covers today and the sentence that it also covers later ones. It is never a catalogue row and never moves between the two panes.
- Advanced access sheet: module, then access level, then either the record transfer list or one switch for a level that is never record-scoped. A switched-off module blocks every add here too, and keeps removal.
- Sample data carries one enabled module with no records of its own, Service requests, so the module row and its grant can be exercised end to end. It carries the missing-role note and the last-administrator guard.
- "Roles assigned directly" is one list in the Advanced sheet. It shows every role this recipient already holds that no level owns, each with its module, its scope, and a Remove control, and below them every role staged to be added, each with a Pending pill and a Remove that takes the addition back. An empty list says so by name.
- Picking a role and a scope adds the request to that list. Removing an existing one stages a removal, marks the row Pending removal, and offers Undo. Nothing is written either way until Save, and one Save writes additions and removals together through the one assignment procedure. There is no second writer and no second callback.
- A removal that the rules refuse is disabled in place with its reason on the row: self-protection for the signed-in administrator's own Tenant administrator role, then the last active holder rule, with the line about giving the role to somebody else first. A switched-off module is never a reason to refuse a removal: a kept grant must always be removable, on this path as on every other.
- Pending bar: sticky at the bottom of the page while anything is unsaved. It counts the changes, splits them into to add and to remove, and holds Cancel and Save changes. Under 768px the primary action also sits in the shell's bottom bar.
- Save shows the button's loading state, then a toast that says the change is written to the audit log.
- Overview: a segmented control, "By group or person" and "By module or record", then one searchable picker. Before a subject is chosen the page shows one card that explains the choice and says that nothing is read before then, which is why there is no all-people by all-records matrix.
- Overview results: a header line with the count and the subject, a search field over the results, a table with Who, Reaches, Role, How, and Added, and a pager of ten rows that names the range and the total. Under 768px the table is a card list.
- A row whose grant does not apply right now carries a "Not in effect" pill with the reason: an archived group, a disabled person, or a module that is switched off.
- A row names another path under How, as "also through <group>", only when the sentence behind it is true: remove this grant, and that same person still reaches that same target with that same permission. Four rules make it so. The path belongs to the same effective person. It carries the same permission key, not merely a similar role name. It applies right now, so an archived group, a disabled person, and a switched-off module are never the path that stays. A whole-module grant covers every record of its module, so it is an alternative path for one record, while one record is not an alternative path for the whole module. A grant made with a role picked directly carries no level, so this read model cannot say which permissions it holds; such a row neither claims an alternative path nor serves as one.
- In a module or a record lookup two unrelated holders of one record are not each other's alternative path, so a row there names one only when a single holder carries both rows.
- Every row names its scope beside the module: "One record" or "Whole tenant". The How column names the source: "Direct assignment" for the subject themselves, "via <group>" for a group path.
- Under the table, one line states that access can arrive more than once and that removing one grant can leave another, and links to the audit log for history.
- Every destructive step uses the confirm dialog from the design system: the title names the object, one sentence of consequence, Cancel focused.
- Tokens: blue for primary actions, links, and the selected row, neutral gray label pills, amber only for a real warning, rounded-xl cards, rounded-lg controls. No screen in this section carries a debug or prototype panel, and no card explains the product at length.
- Out of scope: an all-recipients by all-records matrix, a background access scan, a reporting engine, history of changes (the audit log owns it), and editing a module's own records.
