## Overview
Two admin portal screens behind `core:roles:manage` (R-37e). Grants and Advanced access assign and remove roles after creation. Add assignment on a person, group or module sheet adds an assignment of any role. All of them write through the one role-assignment service (`DEC-39`). Add person offers no role (`d8l5.63`). A group or a person has access to a module exactly when it holds at least one role of that module. Access adds up across direct assignments and groups, and no deny rule exists (R-37a). The everyday flow on Grants has three steps: pick a group or a person, move module rows between Catalog and Granted and pick the role of each Granted row, save. Overview is read-only and answers who reaches which module, with which role, and through which path. Add assignment adds any role: a core role, the Auditor role, a custom role, or a module role at one record of a module that owns records. Advanced access in Grants keeps these roles for bulk work (R-37c). Access belongs to core administration, so it stays reachable when any module is off. Roles keeps role definitions only, and a module's own screens link here instead of editing access themselves (`DEC-39`, one writer). Designed mobile first: the phone layout is the base and desktop adds columns.

## User Flows
- Administrator opens Grants, picks a group from the Groups and people list or the Grant to field, and sees the catalogue at once. No module or role is chosen first.
- Administrator ticks two module rows in Catalog, presses Add 2, and saves. Each row writes one assignment of that module's default access role, which the module declares as `defaultAccessRole` (`../../../architecture/module-contract.md`). The new Granted row names that role and carries the unsaved dot with "(unsaved)" until Save.
- Administrator changes the role choice on a Granted row, for example Invoices from Invoices and Payments viewer to Invoices and Payments editor (renamed 2026-11-08, `czjw.100`). The row carries the unsaved dot, shows the old role struck through, and the pending bar counts one change. Save swaps the role.
- Administrator grants to one person instead of a group. One Grant to field lists groups first and then people. A group is the normal path, because the identity provider keeps it current.
- Administrator ticks a Granted row, presses Remove 1, and saves. A confirmation names every role of that module that goes and every assignment that stays. A removal with no other assignment also asks, because it takes roles. For a person it says "<Name> has no other role of <Module>. After you save, <Name> loses access to <Module>." For a group it says "After you save, <Group> has no role of <Module>. Members keep <Module> if they have it directly or through another group."
- Administrator picks a person whose group already gives a module. Granted lists that assignment as a read-only row, "<Role> · Assigned via <Group>", and the group name opens that group on Grants. A role that includes the module, such as Tenant administrator for Ask, reads "Assigned via <Role> (role)" and opens Advanced access. The Catalog row stays, with "Also assigned via <source>", so a direct role can still be added. Granted then shows both.
- Administrator opens the screen for a tenant with a module that is off. The module takes no new role: its Catalog row reads "Module off" and cannot be ticked, and select all and Add all shown skip it. Its Granted rows stay with "Paused: Module off", the role choice is read-only, and Remove stays available.
- Administrator turns the module on again. The kept assignments apply once more. Nothing is rewritten, because nothing was deleted.
- Administrator sees each direct role that the module rows do not edit, for example Tenant administrator, Auditor or a module role at one record, as a read-only row in Granted with "Change in Advanced access". Nothing is hidden.
- Administrator opens Advanced access and adds or removes a core role, the Auditor role, a module role at one record of a module that owns records, or a custom role. It writes through the same role-assignment service and keeps the same safeguards.
- Administrator tries to remove the last active path to Tenant administrator, or their own Tenant administrator role. The Remove control is disabled with the reason, as on People and Groups. The rule counts the people who would still administer the tenant, not the assignment rows: only an active person counts, a path through an archived group counts for nobody, and two paths to one person are still one person (R-38).
- Administrator saves a batch that the screen believed was allowed, because somebody else removed the other administrator while this page was open. The server refuses, the screen states the reason where the pending count sits, and every unsaved change stays on the screen.
- Administrator changes the recipient with unsaved changes. A confirm step names the count and offers Discard.
- Administrator opens Access and lands on the Overview. Overview opens with every assignment, paged and filtered on the server, newest first, with filter chips for person or group, module and role, and a search (R-37b).
- Administrator reads a row that says "also through Finance team": that same person reaches that module twice, so removing one path leaves the other. Two different groups holding the same module are not each other's alternate path, and the page never says so. The page explains this under the table and links to the audit log for what changed and when.
- Administrator opens How access works beside the catalogue heading and reads that each module has its own roles, that any role of a module gives access, that access adds up, and that a module that is off keeps its roles, but you cannot add new ones. The callout is collapsed until it is asked for.
- Manage in Access on a person, group, role or module opens the Access Overview for it. Grants opens with its recipient filled. The address keeps the filter, so a reload keeps it too (`d8l5.46`). A link that also names a recipient, `/admin/access?recipient=<id>&role=<id>`, stays on Grants: it preselects the module of that role and puts the role in the row's choice, and a link with a core role opens Advanced access (R-37a).

## UI Requirements
- Renders in the admin portal chrome under one page title, Access, with two tabs: Overview, then Grants. `/admin/access` lands on the Overview. The tab is the route, so a link can open either one.
- Grants opens on Groups and people: a search, a Show select (Groups and people, Groups, People), the columns Group or person and Assigned roles, 25 to a page. A row opens its editor, and All groups and people goes back.
- Grants toolbar: Grant to and one recipient picker, groups first and then people, then Advanced access at the far right. A change of recipient never clears the screen. Under 768px the toolbar wraps to two rows.
- The recipient picker holds one line, an icon, the name, and one short fact such as "Group · 17 members" or the email address. It opens a panel with a search field and one list, groups first and then people, each row with its icon, name, and detail. Escape and a click outside close it.
- Help disclosure (design system, Help disclosure): one collapsed button, How access works, beside the catalogue heading on Grants and at the end of the toolbar on Overview. It opens on click, on tap, and on Enter or Space, and Escape closes it. It explains that a role of a module is access and that access adds up. It uses no level words, and it never carries a consequence that the confirmation must carry.
- Catalogue card: the heading "Access assignments", and one line that names the recipient and says that Granted means a role exists and not that the module works today. A Show select (All items, then one entry per caption) at the end of the heading row filters both panes. It shows only when the list has more than one caption. Then the transfer list.
- Transfer list (design system: Transfer list, two-pane form): Catalog on the left, Granted on the right, each with a count, a select-all box, a search field, a quick action for everything shown ("Add all shown", "Remove all shown"), and one button that moves the ticked rows ("Add 3", "Remove 2"). Under 1280 px the two panes stack, Catalog then Granted, each with its own heading, quick action, search and move button. Under 768 px Granted comes first.
- Both panes group their rows under the captions Modules and Core. Every enabled module has a row, also a module that owns records. The Core group holds one row, Ask, which the core system role `Ask user` grants. Solutions join as a third group later (R-37a). The headings are captions inside the pane, never a second bordered box.
- Each Granted row offers the module's roles by name in a select at the sm control height, the default access role first and labelled "(default)", then the other roles in declared order. A module with one role, such as Ask with `Ask user`, shows the role name as static text and no control. On a phone the choice sits on a second line of the row, at full row width.
- A row whose change is unsaved carries the unsaved dot with the hidden text "(unsaved)", or "(unsaved removal)" on a removed row. A swapped role shows the old role struck through under the new one.
- Granted holds the editable row of each direct role, which says Direct, and one read-only row for each other assignment that opens the module. A read-only row has no checkbox. It shows one line, "<Role> · Assigned via <Group>" or "Assigned via <Role> (role)", with the name as a link. A direct role of the row that is not the editable one (one record, or a second role) reads "<Role> · Direct · Change in Advanced access". A role that opens no module has its own read-only row, "Direct · Change in Advanced access". A one-record assignment carries the pill "One record · <record>". A Catalog row that the recipient reaches through such an assignment for all records carries a third line, "Also assigned via <source>". The Granted count counts modules and Core entries, not rows.
- A row whose module is off carries "Module off" in Catalog and "Paused: Module off" on a Granted assignment, with no other line. On the Catalog side its text is muted and its checkbox is disabled. Muted text, not reduced opacity, keeps the contrast at AA (owner review pending, `../../design-system/tokens.md` asks for a dimmed row). On the Granted side the role choice is read-only and the checkbox stays live, so the assignment can be removed.
- Remove confirmation (confirm dialog of the design system, a bottom sheet on a phone): the title names the module and the recipient, "Remove Invoices from Jamie Chen?". The body has one sentence of consequence, a list "Roles that go", and a list "Assignments that stay" with each other assignment and its role. With assignments that stay, the sentence is "The roles that go are removed when you save. Access continues through the assignments that stay." When a group's own role stays after a Remove, the list reads "<Role> · Direct", and no "stays, assigned via" line appears. With no other assignment, the dialog says the person or group sentence of the flow above. Cancel has focus. The action uses the danger tone. The dialog never says that access was revoked when an assignment stays.
- Pending bar: sticky at the bottom of the page while anything is unsaved. It says "<n> unsaved changes", counts them as to add, to change, and to remove, and holds Discard and Save. A swap counts once as to change. Under 768px the primary action also sits in the shell's bottom bar.
- Save shows the button's loading state, then a toast that says the audit log records the change.
- Advanced access: a slide-over of 560px on desktop and a full-height sheet on a phone. The sheet description reads "Extra access for <recipient> that the main list does not cover: admin portal rights, the Auditor role, a role on one record only, and custom roles. Nothing changes until you press Save." At the top one list, "Extra roles of <recipient>", each row with the role, its module or Core, a scope pill (All records or "One record · <record>"), and Remove. With none, it reads "No extra role is assigned to <recipient>." Below, "Add a role": a role picker grouped Core (Tenant administrator, Auditor), Module role at one record, and Custom roles. A module role here exists only for a module that owns records, and then needs one record picked by search. A staged row carries the unsaved dot, and a staged removal offers Undo. One Save writes additions and removals together through the one assignment service.
- A module that is off blocks every add in Advanced access too, with an amber line, "<Module> is off. You cannot add its roles until it is on, but you can remove them.", and keeps removal.
- A removal that the rules refuse is disabled in place with its reason on the row and in its title: "Only another administrator can remove your own Tenant administrator role.", then "This is the last active Tenant administrator. Assign the role to someone else first." A module that is off is never a reason to refuse a removal.
- Overview: a search, then the filters Person or group ("Anyone" while empty), Module and Role. The role filter lists Core first, then each module's roles (`d8l5.46`). A set filter shows as a chip with Clear filters.
- Overview results: the heading Assignments with the count, a table with Role, Assigned to, Scope, Assigned via and Assigned (date and by), 25 rows a page, newest first, and a pager that names the range and the total. Assigned via shows only while the Person or group filter holds a person (OD-10-2). Under 768px the table is a card list.
- Assigned via says "Direct" for the person's own role and "<group> (group)" for a role through a group. Assigned to names the person or group, with "Person", "Group · n members" or "Directory group · n members" under it. Scope says "All records" or the record. A custom role says "Custom role" after its module.
- A row whose assignment does not apply right now carries one pill "Paused: <reason>", with "Group archived", "Person suspended" or "Module off".
- A row names another path as "also through <group>" only when the sentence behind it is true: remove this assignment, and that same person still reaches that same module. The path belongs to the same person, applies right now, and covers the whole module. Groups do not nest, so the read expands a person through their own groups only (R-37d). In a module lookup two different holders are never each other's alternative path.
- Under the table, one line states that access can arrive more than once and that removing one path can leave another, and links to the audit log for history.
- Every destructive step uses the confirm dialog from the design system: the title names the object, one sentence of consequence, Cancel focused.
- Sample data in the prototype is fictional: the tenant Harbor Point, people at `example.com`, and the four built modules with their owner defaults, Invoices "Invoices and Payments viewer" (renamed 2026-11-08, `czjw.100`), Analytics "Analytics editor", Slides "Slides editor", and Placeholder "Placeholder user", plus Ask "Ask user". Analytics is the module that is off.
- Tokens: blue for primary actions, links, and the selected row, neutral gray label pills, amber only for a real warning, rounded-xl cards, rounded-lg controls. No screen in this section carries a debug or prototype panel, and no card explains the product at length.
- Out of scope: an all-recipients by all-modules matrix, a background access scan, a reporting engine, history of changes (the audit log owns it), and editing a module's own records.
