# Genie Ops Center: Product Roadmap

Status: draft for review, 2026-09-16. Sections are ordered by dependency. Each section ends with a definition of done. Decisions and open items reference `vision.md` in this folder.

## Section 0: Monorepo foundation

Goal: one application that composes core and modules, built from one Dockerfile into one image per customer, with the tooling to grow modules without touching core.

Structure: the full tree, the per-customer configuration folders under `customers/<slug>/deploy/`, and the eight levels at which a customer requirement is met are in `../architecture/repository-layout.md`. In short: one app in `apps/genie`, core and ui in `packages/`, one package per module under `packages/modules/<capability>`, Nx generators in `tools/generators`, one folder per customer under `customers/<slug>/` holding configuration and, if needed, a custom app, and the Dockerfile, the stack template, and the Keycloak templates under `deploy/`.

Rules enforced from day one:

- `apps/genie` imports core, ui, and modules. It contains no business logic.
- `packages/modules/*` imports core and ui. A module never imports another module.
- `packages/core` imports ui only.
- `packages/ui` imports nothing internal.
- No code reads the database, settings, branding, entitlements, or files except through the `TenantContext` object (`DEC-34`). Core exports no connection singleton, and `pg`, `drizzle-orm/node-postgres`, and core's connection module are banned imports outside core.
- Enforced by an oxlint `no-restricted-imports` configuration per package layer in `packages/config`, and visible in the Nx project graph (`nx graph`). Nx's own boundary rule runs on oxlint only through the experimental `@nx/oxlint` bridge, so it waits until that bridge is stable (`../core/tech-stack.md`).

Work items:

1. pnpm workspaces with Nx. `nx affected -t build test lint typecheck` in CI, Nx local and remote caching, tasks inferred from package scripts, and project tags that mirror the layers below.
2. Shared config package. Node 26, TypeScript strict, oxlint, oxfmt, lefthook.
3. Module contract in core, as specified in `../architecture/module-contract.md`: identity, schema, router, permission keys, record types, default roles, navigation, pages, configuration schema, events, jobs, inbound endpoints, integration kinds, tests. A placeholder module exercises every point that exists in Section 0 and gains the events, jobs, and entitlement points when Section 1 delivers them. Core ships a stub `can()` that refuses every permission except `placeholder.read`, which the placeholder module declares and the stub grants to every request, until Section 2 item 6 replaces it (`DEC-34`). The placeholder's read procedure checks that permission and then reads through the tenant context, so the router is authorized through the seam from the first day and the isolation test of item 3a has one real read to prove.
3a. Tenant context in core: `createTenantContext()` builds one object from the environment at startup, holding the database pool and the environment values as fixed members; the app passes it into the tRPC context, the job worker, and pages (`DEC-34`). Section 1 adds the file store (item 7) and the settings, branding, and entitlement readers (item 1) to the same object. One integration test builds two contexts against two Testcontainers databases in one process and proves the placeholder module's router never crosses them. It is the standing isolation test.
4. Module registry in the app: `apps/genie/src/modules.ts` is generated at build time from `MODULE_INCLUDE` (default: every module, for development and CI), registers the included modules, mounts routers, renders navigation from the navigation entries the included modules declare. The entitlement filter joins in Section 1 item 1 and the permission filter in Section 2 item 6. An excluded module has no import anywhere in the build (`DEC-22`, `DEC-33`).
4b. Migration histories: core and every module each own a drizzle-kit migration folder and a migrations table. The migrator applies core, then each included module. The Testcontainers preset applies the same set (`DEC-33`).
4a. Nx generators in a local plugin: `module:new <capability>` scaffolds a module package wired to every contract point with passing placeholder tests; `tenant:new <slug>` scaffolds `customers/<slug>/deploy/` with the tenant's configuration and provisioning inputs (`DEC-22`).
5. Docker image. One Dockerfile with `MODULE_INCLUDE` as a build argument, and `scripts/build-customer-image.sh <slug> <version>` that builds and pushes a customer's image by hand or from CI (`DEC-33`). Startup: validate env, connect to the database, apply the core history and each included module's history under an advisory lock with a lock timeout (`LOCK_TIMEOUT_MS`, default 120 seconds) that fails loudly rather than hanging, stay unhealthy if a migration fails so the previous version keeps serving, then serve (`DEC-9`). The same image runs `genie-ops` and the job worker through entrypoint flags.
6. Test infrastructure, in place before the first feature:
   - Vitest for unit tests in every package, with one shared preset in `packages/config`.
   - Integration tests with Testcontainers: a disposable Postgres per test file, the real migration histories applied, factories in `packages/core/testing` for the placeholder module's tables now and for each core table in the section that creates it, and the two-context isolation test from item 3a.
   - Playwright for end-to-end tests: a compose file that starts one deployment with the core history and the placeholder module applied. The Keycloak test realm and the local test identity provider join the compose file in Section 2 item 9, and the seeded deployment in Section 1 item 5. Every test runs at a phone viewport and a desktop viewport (`DEC-25`).
   - An interactive seed for local development, `pnpm seed`, that asks for the customer slug, the modules, and the first administrator email, and runs the same setup as `genie-ops setup`. It arrives with that command in Section 1 item 5.
   - Module contract: a module ships unit tests for its logic, integration tests for its router and schema, factories for its tables, and at least one end-to-end test for its main path. CI fails a module package that has no tests.
7. Developer tooling: TanStack Devtools mounted once in `apps/genie` in development, with the Query, Form, and Pacer panels and a Genie panel (current tenant, user, groups, effective permissions). Only the Vite plugin strips it at build time and this project builds with Next.js, so the mount lives in one file imported through `next/dynamic` behind a `process.env.NODE_ENV === "development"` check, and the packages are development dependencies.
8. CI: lint, typecheck, unit, and integration on every change. End-to-end on every merge to `develop`. On a release tag, build one image per customer folder with that customer's include list and push it as a private image to GitHub Container Registry (`DEC-33`), by calling the build script from item 5. Every customer build must pass typecheck and the smoke test, so core never depends on a module being present.
9. Internationalization scaffold: `next-intl` with one English message catalog; every user-facing string goes through it from the first screen (`DEC-13`).
10. Logging and error responses (`DEC-31`): pino JSON logs with request id, tenant id, and user id on every line; `LOG_LEVEL` from the environment; no secret, session token, or emailed link is ever logged. An API or route error returns a stable code and a safe message; upstream and database error text stays in the log and never reaches the client.
11. Security headers (`DEC-31`), set once in the app for every response: a nonce-based content security policy with `default-src 'self'`, `frame-ancestors 'none'`, and a `frame-src` built per request from the origins each included module contributes through the module contract; `Strict-Transport-Security` with preload; `Referrer-Policy: strict-origin-when-cross-origin`; `X-Content-Type-Options: nosniff`; a minimal `Permissions-Policy`. One end-to-end test asserts the headers on the placeholder module's page. Section 2 extends it to the sign-in page and Section 3 to the workspace shell. The environment variables the image reads are listed in `../architecture/environment-contract.md`.

Done when: the image builds, the app boots against an empty database with only the core history applied, the placeholder module passes through every contract point that exists in Section 0 with the stub `can()` refusing every call except `placeholder.read`, and the three test layers each run green, including the two-context isolation test, with the end-to-end layer run at a phone viewport and a desktop viewport.

## Section 1: Deployment and setup

Goal: one customer's stack goes from an empty database to a running deployment with one command, on Genie's servers or the customer's, from that customer's image.

Work items:

1. Deployment tables in the one database: `tenant_module`, `tenant_api_key`, `setup_step`, `retirement`, `rate_limit_window`, `tenant_settings`, `tenant_branding`, `audit_event`, and the pg-boss schema, in the core migration history. See `../architecture/data-shape.md`. `updated_by_user_id` and `actor_user_id` are nullable here and gain their foreign key in the Section 2 migration that creates `user`. The settings, branding, and entitlement readers join the tenant context here as caches that expire after 10 seconds (`DEC-46`).
2. Not-set-up page: until setup has completed, every route shows a clear page and the health endpoint reports `degraded`.
3. Database access through the tenant context only: one Drizzle pool, built at startup, never exported (`DEC-34`).
4. Migrations at start: the core history and each included module's history applied under an advisory lock, idempotent, also callable as `genie-ops migrate`. Expand-then-contract is guarded by Squawk and `drizzle-kit check` in the pull request pipeline, and every release must upgrade from the last three (`DEC-43`). The migrator logs the count of pending migrations at start. The unauthenticated health endpoint returns only `ok` or `degraded` and never error text (`DEC-9`).
5. `genie-ops setup`, resumable through `setup_step`, with the steps this section has tables for: migrate, insert a `tenant_module` row for every compiled module, seed `tenant_settings` from `tenant.yaml` and `tenant_branding` from `branding.seed.json`, each parsed through its strict zod schema in `packages/core/src/lib/tenant-config/` so that a key in the wrong file fails the command (`DEC-35`), and mark setup complete. The same schemas are what `nx g @genie/tenant:new` validates, and `nx run core:schemas` emits their JSON Schema into `deploy/schemas/` for editors. Section 2 item 9a adds the realm, client, role, group, and break-glass steps to the same command, and a stack set up before that upgrade runs those steps on its next `genie-ops setup`.
6. Stack template in `deploy/stack/`: compose file and Helm values for the application, the worker, and Keycloak, copied by `nx g @genie/tenant:new` into `customers/<slug>/deploy/`. Verified with a smoke test that boots a customer image from its generated compose file and proves an excluded module's tables and routes are absent (`DEC-33`).
7. File storage service in core: `FileStorage` interface with the `postgres` adapter (bytes in `file_blob`), adapter selected by `FILE_STORAGE_ADAPTER`, uploads through the application with a 15 MB limit (`FILE_MAX_BYTES`, raised only with `s3`, `DEC-44`) and type allow-list, the `file_blob` bytes column on external storage, tokenized short-lived download links, `file.scan_status` present and set to `skipped` until a scanner exists. The `s3` adapter is later (`DEC-20`).
7a. Integration records: `tenant_integration` table and a core service that resolves a secret reference for a module at call time. No connector and no screen are built in core; the first module that needs a connector builds both through its pages slot (`DEC-20`).
8. Mailer service in core: hosted provider adapter and SMTP adapter behind one interface. Every template has an HTML and a plain-text part. In production, an action that must send an email (adding a person in invite mode, which sends the invitation) fails before it creates anything if no mailer is configured; links with tokens are never written to logs. `genie-ops setup` and `genie-ops admin add` send no email: they pre-add a pending person, and the first sign-in activates them, so setup runs without a mailer. A local-accounts realm sends its own set-password, reset, and verify emails through the realm's SMTP settings (`DEC-10`), never through this mailer. Template catalogue: invitation (brokered and local-account variants), role granted or removed, new-device sign-in, module notification.
9. Job queue: pg-boss in the deployment's database, one worker process from the same image selected by an entrypoint flag (`DEC-12`).
9a. Event bus in core: typed `emit` and `on`, in-process for fast handlers, pg-boss-backed for slow or retryable ones, plus `provide` and `capability` for the capabilities channel. Notifications, email, and audit are the first subscribers. The placeholder module exercises both channels; no shipped module provides a capability yet. Modules emit; they never call each other.
10. `genie-ops` command line inside the image: `setup`, `idp set`, `admin add`, `module enable|disable`, `break-glass rotate`, `migrate`, `retire` (`DEC-14`). The runner, `setup`, `module enable|disable`, `migrate`, and `retire` land here; `idp set`, `admin add`, and `break-glass rotate` land in Section 2 item 9a with the tables they write. `admin add <email>` pre-adds the person as pending in `Genie Administrators`, or adds an existing person to that group, sends no email, and writes an audit event. It is the recommended administrator recovery path (`DEC-23`). Every command writes one `audit_event` row, `ops:<command>`, with the operating-system user, the non-secret arguments, and the outcome, through one helper in the command runner (`DEC-45`).
11. `PUBLIC_URL` as the one public address; the reverse proxy owns the certificate (`DEC-19`).

Done when: a customer image boots from its generated compose file and shows the not-set-up page, `genie-ops setup` completes and clears it, every `genie-ops` command run leaves one `audit_event` row, and a second stack of the same image with a different database shows none of the first stack's data. No sign-in exists yet; Section 2 proves it.

## Section 2: Identity and access

Goal: a customer employee signs in with their company account through Keycloak and sees only what their roles allow. Offboarding in the identity provider locks them out at the next sign-in, and an open session ends at the idle timeout or at the 24 hour cap at the latest (`DEC-46`).

Work items:

1. Better Auth: one instance built at startup inside the tenant context, using the `genericOAuth` Keycloak provider with the realm issuer from `KEYCLOAK_URL` and `KEYCLOAK_REALM`. Callback path `/api/auth/callback/keycloak`, sign-in through `signIn.social`, and `encryptOAuthTokens` on, because nothing reads the stored identity-provider tokens.
2. Account linking trusted for `keycloak`. Onboarding mode from `tenant_settings` (`DEC-7`): in `invite` mode an unknown email is refused with a clear message and a pre-added pending person is activated on first sign-in; in `jit` mode an unknown email is created active. Add person in People works in both modes, with roles assignable before first sign-in.
3. Break-glass admin: email and password enabled, seeded at provisioning, hidden from the sign-in page, reachable at `/admin/login`.
3a. Local accounts (`DEC-10`): when `tenant_settings.local_accounts_enabled` is on, "Add person" creates the account in the tenant realm through the realm's admin service client and triggers Keycloak's set-password email; the `user` row is created pending as in invite mode. Password reset is a link to the realm's own reset flow. Realm template variant: no identity-provider redirect, email verification on, password policy, brute-force protection, optional authenticator-app required action, per-realm SMTP.
4. Sessions: idle timeout from tenant settings (default 15 minutes), checked by the application on every request through the settings reader against the session's last activity, with Better Auth `expiresIn` as a fixed 24 hour absolute cap (`DEC-46`), database-backed, no cookie cache, `freshAge` disabled so the sessions list keeps working for people whose sliding session is older than a day, IP address resolved through the deployment's trusted proxy list. Activity in the browser slides the server session, throttled to half the idle window; the idle warning fires before server expiry so "Stay signed in" always lands inside the window. Sign-out ends the Genie Ops Center session and then the Keycloak realm session through the realm's logout endpoint (`DEC-11`). The account page starts here with the person's own sessions and sign-out everywhere; Section 2 item 11 and Section 3 item 7 extend it.
4a. Rate limits (`DEC-31`): sign-in brute force is the realm's job (Keycloak brute-force protection in the realm template). Genie Ops Center limits its own sensitive endpoints: add person, resend set-password, and break-glass sign-in attempts, with a fixed window stored in the database, and every refusal is an audit event. A counter row is keyed by endpoint, subject, and window start and is overwritten by the next window, so no sweeper job exists.
5. Groups from the token: a normalized `groups` claim mapped in Keycloak from whatever the identity provider sends (an OIDC groups claim, a SAML attribute, or LDAP `memberOf`). Local groups allowed as a fallback. One sync function in core, tested for absent, empty, and present claims: a present claim replaces the `idp` memberships, an absent claim keeps them and writes the audit event `auth:groups_claim_absent` (`DEC-41`).
6. Roles and permissions: `role`, `role_assignment`, the single `can(user, permission, resource?)` seam with no bypass except `is_break_glass`, and `scopesFor(user, permission)` for list queries, sharing one per-request loader and one test suite with `can()` (`DEC-39`, `DEC-48`). Modules declare permission keys and default roles; enabling an entitlement appends the module's admin key to `Tenant administrator` (`DEC-23`).
7. People, Groups, and Roles screens in the admin portal, with server-enforced self-protection: no one can disable or remove themselves, and the last `Tenant administrator` cannot be removed or demoted. For a pending local-account person, "Resend set-password email" through the realm.
8. Audit writes: the `audit_event` table from Section 1 item 1 is written by core for sign-in and admin actions, and by modules for record changes. Core also emits `core:session:new` on a sign-in from a device not seen before, which writes an in-app notification for the person, and `core:role:granted` and `core:role:revoked` on an assignment change, which send the role email from the mailer catalogue. The `notification` table is created here, in the same migration, and is written by the same events that send email. The inbox screen is later (`DEC-21`).
9. Keycloak realm template and runbook: create a realm, add the customer's identity provider (OIDC, SAML, or LDAP), map groups, set the identity-provider redirector default, create the `genie-ops-center` and `genie-studio` clients (`DEC-8`) and the `genie-admin` service client with user-management rights for the realm, set trust email and PKCE. Two variants: brokered and local accounts (`DEC-10`). The template is a realm export checked into `deploy/`, applied by `genie-ops setup`.
9a. Identity steps of `genie-ops setup`, appended to the resumable command of Section 1 item 5: create the realm from the template variant that `local_accounts` selects plus `realm.overrides.json` (`DEC-36`; the identity provider itself is added afterwards by `genie-ops idp set`), create the clients, seed the core system roles and the `Genie Administrators` group with the initial administrators from `tenant.yaml` as pending members, seed every enabled module's default roles, and create the break-glass account with a generated password printed once for the operator's secret store (`DEC-23`, `DEC-24`). `idp set`, `admin add`, and `break-glass rotate` land here with their tables.
10. Keycloak hardening: replace the temporary bootstrap admin, external backed-up database, more than one node, monitoring.
11. Break-glass lifecycle: authenticator app required through Better Auth's two-factor plugin, forced password change and enrollment on first sign-in with a limited session until both are done, the shared password rule (14 characters, three of four classes), `genie-ops break-glass rotate` revoking sessions, an account page variant with change password, re-enroll, and sessions, hidden from People, Groups, and Roles (`DEC-15`, `DEC-24`).
12. Audit reader: `core:audit:read` permission and a filterable audit screen in the admin portal, with a filter for operator rows (`DEC-45`). Export and SIEM push are later (`DEC-16`).

Done when: `genie-ops setup` on a fresh stack creates the realm and the first administrator signs in, a person assigned in a test identity provider signs in once, appears in People with their groups, receives a role through a group, and sees the module that role grants. Removing them in the identity provider blocks their next sign-in.

## Section 3: Shell, branding, and design system

Goal: the new shell and tokens the design owner delivers, implemented once, with the tenant branding layer on top.

Work items:

1. Fixed token layer from the design owner: type scale, spacing, radius, motion, neutrals. Every screen in this and later sections is designed mobile first; tables become card lists and inspectors become full-height sheets on small screens (`DEC-25`).
2. Tenant token layer: primary color and its derived foreground, font size preset, text color, logo, favicon, company name, emitted as CSS variables per request from `tenant_branding`. The color variables are `--primary` and `--primary-foreground` only, and no tint ramp is derived from the tenant color, because every tinted surface stays a fixed neutral gray (`DEC-47`).
3. Primitives in `packages/ui`: Button, Input, Select, Dialog, Table, Toast, Switch, Tabs, and one form-control height scale.
4. Shell in core: navigation from entitlements, permissions, and core categories (`DEC-51`), account menu, idle-timeout handling, empty state when a person has no grants.
5. Branding pages in the admin portal, one tab each: Identity (names, logos, favicon), Colors and theme (primary color, default theme, contrast check), Typography (font from the approved list, font size preset, text color, contrast check), Sign-in page (background, welcome text, support contact, system-use notice), Email (sender, reply-to, footer), Links (support, terms, privacy), Locale (language, time zone, formats). Live preview on every tab.
6. Sign-in page and React Email templates read the tenant branding. Nothing from branding is written to the realm. A local-accounts realm sends set password, reset password, and verify email with Keycloak's built-in templates, which print the realm display name that provisioning set to the company name (`DEC-40`).
7. Personal overrides on the account page from Section 2 item 4: language, time zone, and theme, stored in `user_preference` and read by the shell when it resolves locale and theme.
8. Section designs reviewed one at a time as the design owner delivers them.
9. Accessibility: WCAG 2.1 AA target, axe checks in the Playwright suite, manual review per section design (`DEC-21`).
10. Tenant Settings page in the admin portal, behind `core:settings:manage`: onboarding mode, local accounts, and session idle minutes from `tenant_settings`, plus one configuration card per entitled module rendered by `ConfigForm` from the module's `configSchema` (`DEC-28`). The placeholder module shows all five field kinds. Every save is an audit event.
11. Modules and Categories pages in the admin portal, behind `core:settings:manage`. Modules lists every compiled module with an enabled switch that writes `tenant_module.enabled` through the same core procedure as `genie-ops module enable|disable`, a category picker that writes `tenant_module.category_id`, and the groups and people holding a role that carries the module's `<id>:use` key, read from `role_assignment`, with a link to Roles. Categories manages the core `category` table, counts members from `tenant_module.category_id` only, and a deleted category leaves its members ungrouped. Every change is an audit event (`DEC-50`, `DEC-51`).

Done when: a branding change shows on the sign-in page, the shell, and an email, in light and dark themes, and the screens pass the accessibility basics (focus order, contrast, reduced motion).

## Section 4: Solutions module

Goal: the solutions catalogue delivered as the first real module, so the module contract is proven on known behavior before any customer module. Module detail lives in `../modules/solutions/README.md`; this section holds only what the core must do.

Work items:

1. The module registry mounts the solutions module through the module contract with no special case: schema merged, router mounted, permission keys registered, default roles seeded on entitlement, navigation entries with their core category ids rendered in the one tree (`DEC-51`).
2. The `can()` seam resolves a record-scoped assignment (`solution:<id>`) end to end, from role assignment to navigation to a server-side refusal, and the workspace solution list is paged on `scopesFor()` so a chat user sees only their solutions (`DEC-39`).
3. The streaming route pattern (server-side proxy, per-user lease) is provided by core so a later module can reuse it. The proxy's allowed origins are an operator setting, `GENIE_CHAT_API_ALLOWED_ORIGINS`, validated at startup with the other environment values; empty disables the route and the admin screens show a notice (`DEC-30`).
4. Entitlement gating proven: with the module compiled in but `tenant_module.enabled` off, nobody sees it and every module route refuses; with the module excluded from the image, its routes and tables do not exist.
5. The module's tests run in the three layers through the shared presets, with no module-specific CI configuration.

Done when: the module described in `../modules/solutions/README.md` meets its own definition of done using only the module contract, and a second, empty placeholder module mounts through the same registry with no core change.

## Customer modules

Customer modules are not core roadmap sections. Each module has its own roadmap in `../modules/<module>/README.md`, with its own phases, open decisions, and customer discovery questions. A module may start once Sections 0 to 4 are done and its own discovery has closed. The core commits to the module contract and to the services modules need (object storage, mailer, audit, permissions, file table), all of which Sections 0 to 3 deliver.

## Section 5: Operations

Goal: a new Genie-hosted customer goes from contract signature to a running deployment in one working day, and a customer-hosted one in one week.

Work items:

1. New-customer runbook: `nx g @genie/tenant:new <slug>`, fill `tenant.yaml`, build and push the image, create the stack in Coolify or hand over the compose file, `genie-ops setup`, set the identity provider, smoke test, branding handover.
2. Three hosting runbooks (`DEC-33`): Genie-hosted on Coolify; customer-hosted and Genie-managed, with the customer's host added to Coolify as a remote server over SSH; customer-hosted and customer-managed, with pull, run, upgrade, and break-glass held by the customer. Delivery is the private image on GitHub Container Registry with a read-only token per customer, or the `docker save` release file for a site without internet. Checklist, recorded in the customer's runbook and not in `tenant.yaml` (`DEC-35`): hosting mode, target host, Postgres, SMTP, Keycloak own or supplied, object storage if any.
3. Health checks, log shipping, and backups (`DEC-31`): a nightly logical backup of every Genie-hosted database, kept 30 days, with a restore drill on staging every quarter. A customer-managed deployment backs up its own database; the runbook states what to back up. Default targets until a customer contract states others: 24 hours recovery point, 8 hours recovery time. The runbook records the drill.
4. Upgrade path: a release tag builds every customer image; Genie-hosted and Genie-managed stacks upgrade through Coolify; a customer-managed stack pulls the next tag; every release upgrades from the last three (`DEC-9`). Kubernetes with one namespace per customer and a rollout tool is the path when the count of stacks makes Coolify slow (ADR 0007).
5. Cross-product step: each genie-studio deployment is configured with its tenant's realm issuer and the `genie-studio` client credentials from the realm template (`DEC-8`). Part of the new-tenant checklist for customers with both products.
6. Environments: dev, staging, and production as three Genie-hosted stacks of a demo customer. A customer's UAT is a second stack of that customer (`DEC-18`).
7. Offboarding: `genie-ops retire` stops the stack and records the date; after 90 days `genie-ops retire --confirm` deletes database, realm, and bucket unless held. Personal erasure anonymizes the user row and keeps audit (`DEC-17`).
8. Later capabilities, tracked but not scheduled: SCIM provisioning, Keycloak page branding per realm, audit CSV export and SIEM push, ClamAV upload scanning, in-app inbox screen, support impersonation with consent, operator console, Kubernetes rollout for many stacks.

## Order and parallelism

Sections 0, 1, and 2 are sequential and are the foundation. Section 3 starts when Section 1 is done. Its items 1, 2, 3, 6, 8, and 9 run in parallel with Section 2; items 4, 5, 7, and 10 need the access seam and the account page from Section 2 and follow it. Section 4 starts when Sections 2 and 3 are done. Section 5 runs alongside from Section 1 onward. Customer modules start after Section 4 and their own discovery, in the order their module READMEs state.
