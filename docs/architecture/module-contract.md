# Module Contract

Status: draft for review, 2026-09-16. This is the single list of what a module may declare and what core provides. Customer modules are unknown in advance, so the rule is: a module uses these points and nothing else, and when a module needs something not on this list, the list is extended in core once, in the same change, so every later module gets it. A module never reaches around the contract.

Package names and folder basenames follow [Module package naming](repository-layout.md#module-package-naming). The module ID stays unprefixed: `contract-data` maps to `@genie/module-contract-data` in `packages/modules/contract-data/`. Package naming does not rename routes, permissions, entitlements, migration identities or selection IDs. Data-only metadata checks own package/folder/ID consistency; runtime declarations remain module-owned.

## What a module declares

Permission keys and default roles follow [Permission and system-role evolution](permission-evolution.md). Registration/seeding creates missing definitions, not new assignments or silent privilege expansions. Renames, retirement, and permission-affecting upgrades require the explicit migration and verification policy there.

| Identity | `id` (kebab-case), display name, version, optional one-line description (shown on the Modules page) | Entitlements, navigation groups, permission key prefix |

| Record types | Types a scope can point at, each with an optional list of parent types and a resolver `resolve(ctx: { tenant }, id)` to `{ label, path?, permission?, parents? }`, where `parents` lists the record's parent scopes as type and id pairs, one per declared parent type. The resolver reads through `ctx.tenant`, the request's own context, never a connection or a cache of its own (`DEC-34`; amended 2026-09-27). Core drops a returned parent whose type is not a declared parent type. Core renders a link only when `path` is present, and `path` must be a route the caller may open under `can()`: `permission` names the key the path requires and defaults to the owning module's `<id>:use`, so a workspace record is use-gated and an admin route can name its own admin key (`DEC-39`; permission added 2026-09-27). The resolver's `label` and the fact the record still exists are live data and travel under the same record check: a caller who may read the event but not open the record sees neither. `can()` matches a resource against its own scope and the parents the resolver returns; `scopesFor()` returns parent scopes unchanged and the module filters on its parent columns (`DEC-39`). Core declares its own record types `user`, `group` and `role` in the same shape, resolved before any module's, each with its admin screen and `?selected=<id>` as the path and its own manage key as the permission | The scope picker in role assignment, the Access overview, the audit reader's link to a target that still exists |
| Default roles | Named permission sets, including `<Display name> user` carrying `<id>:use` for a module with a workspace entry (`DEC-50`) | Seeded by core's `seedRoles` for every compiled module, enabled or not, marked system; seeding inserts a missing role by name and never rewrites an existing role's permissions (R-33a, R-55) |
| Permission transformations | Optional `permissionTransformations`: versioned data, each `{ id, release, description, change }`, where `change` renames one of the module's own keys, revokes one, or renames the display name of one of its own system roles. An id is permanent and never reused. `validateModule` refuses a duplicate id or a key of another module. Added 2026-09-27 (R-33c) | Core's migrator run applies each one once, after every history, in one transaction under its advisory lock, and writes its `audit_event` row in the same transaction. A module's own SQL never writes core tables. See [Permission and system-role evolution](permission-evolution.md) |
| Navigation | Static workspace entries and admin entries, each with its required permission, as `{ pinned: Entry[] (at most six, ordered), entries: Entry[] }`. A static entry carries no category. Core places a module's static workspace entries under `tenant_module.category_id`, groups them by its own `category` table, sorts inside a category by label, puts an entry with no category or with a category that no longer exists in the workspace block, renders one tree, and persists collapse state per device (Spec 3 R-29, R-91). Core never reads a module table to build it (`DEC-51`). Per-request record entries that carry a category arrive with the Section 4 navigation hook. One workspace entry can be marked the landing route, and core sends a person there after sign-in (`DEC-49`) | The shell renders only what the person may reach, including the pinned rail and the category tree, and opens the landing route after sign-in |
| Pages | Page components for workspace and admin, designed mobile first | Thin route files in the app |
| Category assignment | Optional module-owned `listAssignable` and per-record assign/clear contribution, using tenant/caller context and authorized record descriptors | One Categories page combines whole modules and contributed records, including solutions. Core owns whole-module placement; modules own record reads/writes, permission checks and audit. See Category assignment boundary below. |
| Configuration schema | Optional `configuration` (`schema`, `section`, `fields`; named `configSchema` before 2026-10-22), whose `schema` is a zod object limited to string, number, boolean, enum and string list (DEC-28). An enum can give each choice a readable label as a union of string literals titled with `.meta({ title })`, which `z.toJSONSchema` emits as `anyOf` of `{ type: "string", const, title }`. The form shows the title, or the raw value when a choice has no title. The configuration has stable section/field ids, titles, descriptions, optional search keywords and an optional additional section permission | Tenant Settings uses Navigator A: section navigation and a selected detail form, not all module forms stacked together. `ConfigForm` validates in the browser with a validator built from the JSON Schema of that zod schema, and the server validates with the zod schema itself (Spec 3 R-77, amended 2026-10-25); values remain in `tenant_module.config`. See Settings discovery and authorization below. A module that needs richer forms ships its own settings page. A configuration error message (zod custom `error` functions and refinements) never includes the submitted or stored value, because `module-config-invalid` issues reach the browser (R-80, R-84a). Zod's default messages already comply. |
| Events | Named event types the module emits, each `defineEvent({ name, version, payload })` with a versioned payload schema; an event only its own module handles is declared inside it, an event another module subscribes to is declared in `packages/core/contracts` and both import it from there (`DEC-42`) | The typed event bus: `emit` inside `withTransaction`, delivery to fast and durable subscribers |
| Subscriptions | The events a module handles: `subscriptions: readonly { event, handler, name?, durable?, serializeBy? }[]`, validated by `validateModule`. No option is a fast in-process handler; `durable: true` runs as a pg-boss job enqueued inside the emitting transaction; `serializeBy` implies durable and serializes per key. One module may subscribe more than once to the same event. A durable or serialized subscription carries a required kebab-case `name`, unique within its module; `validateModule` rejects one without it, and `name` is ignored for a fast subscription | `registerModuleRuntime` registers them on the context; the worker drains each durable subscription's queue under the owning module's entitlement. The queue name is `event.<module id>.<event name>.v<version>[.fifo].<name>`, never the declaration index, so reordering same-mode subscriptions between releases keeps every in-flight job on its handler. A subscription name is permanent like an event version: a rename changes the queue name and strands the jobs queued under the old one. A serialized queue's `key_strict_fifo` policy runs one key at a time while keys run in parallel |
| Capabilities | Interfaces from `packages/core/contracts` the module provides, each provision carrying its implementation and recorded under the owning module's id | Another module asks core for a provider at runtime through `context.capabilities.get(name)` and gets it or nothing; a name several modules provide makes `get` refuse, because only `list(name)` can tell them apart. `list(name)` answers every provider of an enabled module with its module id, in registration order, skipping a disabled module (`DEC-29`, amended 2026-10-27) |
| Datasets | From Section 7 (`DEC-54`): `datasets: readonly DatasetDeclaration[]`, each named `<moduleId>.<kebab-name>`, with a `description`, the module's own `permission`, `fields` keyed by the name the source select gives each column, a `timeField`, a `recordKey: { type, field }`, an optional `currencyField`, and an async `source(ctx, asOf)` that answers a `DatasetSource` (`{ as(alias: string): Subquery }`) over a Drizzle select already filtered by `scopesFor()`. `source()` must answer a plain, non-thenable `{ as: (alias) => select.as(alias) }` wrapper, not the Drizzle select itself: a select is thenable, so an async function returning it resolves to rows, and core refuses an answer without a callable `as`; `asOf` is the reporting date (Spec 7 R-9), the stored date or today in the tenant's default time zone. A field has a `kind` (`dimension` or `measure`, for the agent only) and a `type` (`text`, `date`, `number`, `money` or `boolean`); a `money` field holds integer minor units (cents) of the row's currency. `validateModule` refuses a name without the module prefix or declared twice in the module, a permission the module does not declare, a `timeField` that is not a declared `date` field, a `recordKey.type` outside the module's record types, a `recordKey.field` that is not a declared `text` field, and a `money` field with no declared `text` currency field | `registerModuleRuntime` registers each one on `context.datasets`, a `DatasetRegistry` that stays empty until it runs and whose `register` throws on a name already registered, keeping the owning module id. Core's dataset service answers the generic query shape for one caller, under `can()` on the dataset permission, with a row cap and a time limit, and composes only over the aliased subquery `source()` returns, so core never names a module table. The query shape is `{ select?, filters?, groupBy?, aggregates?, orderBy?, limit? }`: filters `eq`, `neq`, `gt`, `gte`, `lt`, `lte`, `in` (1 to 1,000 values), `between` (inclusive) and `isNull`, the ordering operators on date, number and money fields only; a group on a field, a `month` or `week` bucket (weeks start on Monday) on a date field, or 1 to 20 labelled, non-overlapping `ranges` (`min <= value < max`) on a number field; aggregates `count`, `sum` and `avg` (number or money), `min` and `max` (date, number or money); `select` or `aggregates`, never both; unique output names. A result holds at most 1,000 rows and says when it was `truncated`, and the query runs read-only and stops after 5 seconds. A `sum` or `avg` over a money field needs one currency in the rows it covers, or a group on the currency field. Every money aggregate (`sum`, `avg`, `min`, `max`) whose covered rows hold one currency carries it. `queryDatasetSeries(ctx, { series })` runs one query per series, each on its own dataset and permission, with exactly one group and one aggregate, no `select`, `orderBy` or `limit`: every series groups x the same way (a plain field of one type, the same `month` or `week` bucket, or the same ranges in the same order), and the answer holds every x value of any series once, sorted, with a missing value `null` and never zero (R-7). Refusals: `not-found` (an unknown dataset, or a disabled module's), `forbidden` (no dataset permission), `dataset-query-invalid` (400, with an issue per part, before any SQL), `dataset-mixed-currency` (400) and `dataset-timeout` (503). Analytics, Slides and the boss agent read data only this way |
| Jobs | Named job handlers and optional schedules, each named `<moduleId>.<name>` | Run by the core worker on pg-boss, each handler given the tenant context. The worker checks the module's entitlement before it fetches a job, so a job of a disabled or unseeded module stays queued, and it schedules a declared schedule only while the module is enabled, under a `genie.module.` key that `jobQueue.schedule` refuses. A job runs at least once, so every handler is idempotent: a job still running when the shutdown timeout passes is failed and retried by its policy, and the late result is dropped. A declaration may set `retry`: a `limit` of retries, a `delaySeconds` and an exponential `backoff`, whole numbers from 0, which `validateModule` checks; without it, pg-boss's defaults apply (two retries, no delay). The worker writes the policy onto the job's queue at every start, and `enqueueJob` writes it onto each job. A module procedure enqueues its own job with `enqueueJob(ctx, job, data)`, which records a signed-in caller under the reserved `genie:startedBy` key, replacing any value the data carried. The public `jobQueue.enqueue` and `jobQueue.schedule` strip that key from their data, so a raw enqueue or a schedule always runs with no caller. The worker strips that key from the data and builds the starter's principal once per run with `principalFor`, with their grants as they are at the run, and passes it as `ctx.caller`; a scheduled run has none. The placeholder module declares `placeholder.read-record` and `placeholder.touch-record`, which its `touch` procedure enqueues (Spec 7 R-12, AC-3) |
| Inbound endpoints | Route handlers under `/api/m/<id>/...` | Authenticated by a tenant API key or a signed webhook secret held as a `tenant_integration`; never by a user session |
| Integrations | Kinds of external system the module can connect to | `tenant_integration` records and secret resolution |
| Content security policy | Optional `contentSecurityPolicy: { frameOrigins(ctx: { tenant: TenantContext }): Promise<readonly string[]> }`; origins computed per request from the module's own records through the supplied tenant context | The security headers set once in the app (`DEC-31`); see provider rules below |
| Tests | Unit, integration, factories, one end-to-end main path. Since Section 2 item 6 the stub is gone: a generated module's integration suite proves its authorized read with a real role assignment through `insertPersonWith` and `principalFor` from core, and keeps its refusal cases; no test fakes a permission answer or uses a test principal. Until sign-in exists (S2-04) the browser layer proves navigation omission and route refusal only; the signed-in browser success path at both viewports belongs to S2-04. Unit/integration/E2E run at both stages; modules with UI also ship documented Storybook stories and applicable browser interaction tests through the shared host. | CI gate |

### Migration declaration and authoring

The integrated Section 0 contract defers migration reads: `schema.migrations` is a function returning the module's migration metadata. Declare each journal entry's SQL file with a static `new URL(..., import.meta.url)` in the owning module, and call core's `migrationsFromJournal(journal, files)` inside that function. `moduleHistory` invokes it during bootstrap planning. Importing the declaration must not read SQL, connect to a database, or run migrations.

After changing the schema, run the module's drizzle-kit generation command, then add each new journal tag and its corresponding file URL to the declaration in the same change. Keep journal order and existing history semantics. A missing declared file fails when the history is read. The module continues to own its drizzle-kit folder and ledger table; this is not a second registry or an eager import-time migration read. The accepted example is `packages/modules/placeholder/src/schema.ts`.

Migration SQL is server-only. The standard app's build validates and removes generated public SQL duplicates while preserving server assets; authored public SQL fails the build. Keep migration declarations outside browser imports. Built-image acceptance must retain unavailable public SQL URLs, no migration contents in served assets/browser bundles, and correct real-database application with source/ledger hashes. Generator templates consume this contract, not the withdrawn raw/bytes-import alternatives. See the F2 decision and evidence in the S0-05 ticket.

### Content security policy provider

The enforced baseline (DEC-31, amended 2026-09-19) is `base-uri 'self'; object-src 'none'; frame-ancestors 'none'; frame-src 'none'`. On viewer documents core replaces only `frame-src` with validated owning-module origins. The core file download route sends the core `DOWNLOAD_POLICY` instead of the baseline (DEC-31, amended 2026-10-26); a module cannot change either. The app emits exactly one final enforced policy, not an additional deny-frames policy. No `default-src`, `script-src`, `style-src` or nonce wiring is required; strict script/style CSP and report-only evaluation are deferred. This removes no authorization, sandboxing, safe-rendering or tenant-isolation requirement. It does not constrain other resource types or force every page to render dynamically. Remote sites' own embedding restrictions still apply.

The provider is server-only and returns HTTPS origins, not full URLs, wildcard patterns, CSP keywords, or header fragments. An omitted provider or an empty result contributes no origins. It receives the deployment's `TenantContext`, never opens its own connection, and never reads another module's tables. The result is deployment-wide frame policy metadata, not a grant to view a record; page and record authorization remain behind `can()` and `scopesFor()`.

Core validates and deduplicates the returned origins before the app composes `frame-src`. Invalid contributions or provider failures must never fall back to a wildcard or the broad `https:` source; the response must not permit frames from a failed contribution. Core owns policy serialization, and modules cannot replace other CSP directives. The provider runs only for iframe-viewer document requests, so a change in its backing records is reflected on the next full viewer document response; a document already open retains its existing policy until reloaded.

Scope confirmed during the Spec 0 review: ordinary pages, API/oRPC calls, chat streams, health checks, static assets, and background prefetch/RSC requests must perform no frame-origin lookup. The app's server-owned route mapping identifies iframe viewer documents and their owning module; only that included module's provider is invoked. Entering an iframe viewer uses a full document navigation, including from the client-side shell, so its response installs the viewer policy before the iframe renders. Broader dynamic origin-policy coverage is deferred until a customer requirement justifies it. Ordinary security headers remain in place everywhere; the narrowed scope concerns database-backed iframe-origin computation only.

The placeholder supplies one fixed HTTPS origin in Section 0. A generated module includes a typed empty provider that contributes nothing until the module needs frames. Contract tests cover omission, empty output, duplicate origins, invalid values, and provider failure. The app's response-generation lifecycle and coverage are specified in the security-header requirements of the foundation specification.

## Category assignment boundary

Accepted 2026-09-19 (DEC-51 addendum). One Categories page assigns both whole modules and module records. Its core entry permission is `core:settings:manage`; providers additionally enforce their own record-management permission on reads and writes (Solutions uses `solutions:admin`). Core dispatches through the compiled registry, never imports module internals or accesses module tables. `listAssignable` returns authorized module/record identity, label and current category, not secrets or unrelated internal data.

Each write targets one record and a core category id or no category. Validate the category through core; recheck caller, tenant, module availability and record authorization at write time; audit successful changes in the owning module. Multi-row interactions report per-row outcomes and support retry, not a cross-module transaction. Placement never grants access. Disabled compiled modules retain record placement but contribute no editable record rows; excluded modules contribute nothing. Core placement of whole modules with static workspace entries remains available when disabled. Do not fall back to cached record rows or direct table access. Category summary counts remain whole-module counts only. Deletion touches no module table; missing category ids render ungrouped.

Section 0 declares/tests this optional interface with a synthetic placeholder without implementing runtime or broadening the authorization stub. Section 3 provides the common page/dispatch and core placement; Section 4 supplies Solutions' provider. Exact transport names are implementation choices, not new prescribed endpoints or tables.

## Settings discovery and authorization

Accepted 2026-09-19. Central settings reads, writes, section navigation and search require `core:settings:manage`. A section's optional additional permission is an AND restriction, never a substitute. Module administration alone does not grant central Settings access. Filter unauthorized metadata before returning it to the browser; direct links and saves enforce the same rule server-side.

Fuzzy search uses authorized section/field names, descriptions and keywords only, never saved values or secrets. Results open the section and focus the field or section heading. Stable ids support links; stale, absent and forbidden targets fail safely without disclosing hidden metadata. This adds neither cross-record search nor a sixth field kind/form engine.

Compiled disabled modules with a schema remain configurable through this authorized core pre-enable path, independently of disabled module routes. Saving never enables a module or bypasses reintroduction review. Excluded modules and modules without schemas contribute no section/search entries. Section 0 declares/tests metadata and permission shapes; Section 3 implements navigation, search, authorization and independent section saves. Preserve edits on refusal and ask before navigation discards them.

## What core provides to a module

- Tenant context: one object with the database connection, settings, branding, entitlements, and file store, passed into every procedure, job, and page. It is the only way to reach any of them (`DEC-34`).
- oRPC base and the contract seam ([ADR 0011](../adr/0011-replace-trpc-with-orpc.md)): a module's `contract.ts` imports only zod and the browser-safe `@genie/core/rpc` entry (`oc`), and is published as its `./contract` export; its router comes from core's `implementModule(id, contract)`. `implementModule` builds the router against the module request context, attaches the entitlement gate (`ctx.tenant.entitlements.isEnabled(id)`) and then the session check on the root `implementer.use()`, and throws the catalogue `AppError` `module-disabled` (with the request id) when the entitlement is off, before any input is parsed. A module never imports `@orpc/*`: the oRPC helpers reach it only through `@genie/core/rpc`, whose entry file exports only browser-safe values (`oc` from `@orpc/contract`, and `appErrorData`). `implementModule`, the conformance check, and the server-side caller `callProcedure` live beside that entry and are exported from the core root, never from `@genie/core/rpc`; tests call procedures through `callProcedure` instead of importing `@orpc/*`. Core records each router `implementModule` builds as `{ id, contract }`, and module validation refuses a router core did not build for that id, a contract that is not the declared one, and any contract procedure that `traverseContractProcedures` finds but the router does not resolve; the same check covers a router built through a dynamic `import("@orpc/*")` that lint cannot see. Core does not re-export `ORPCError`: a module's `can()` denial throws the catalogue `AppError`.
- oRPC confinement, so a later 2.x upgrade touches only these files: one oxlint `no-restricted-imports` rule bans `@orpc/*` everywhere except core's `packages/core/src/lib/rpc/`, the app's `apps/genie/src/rpc/` (handler options, error interceptor, browser client), the route file under `apps/genie/src/app/api/rpc/`, and the OpenAPI build script (`../adr/0011-replace-trpc-with-orpc.md`).
- Identity and access: the current user, groups, `can(user, permission, resource?)` for one resource, `scopesFor(user, permission)` for a list query (`DEC-39`), and the assignment tables. Both functions read the person's assignments once per request and answer later calls from that read, so a role change applies on the next request (`DEC-48`).
- Files: `FileStorage` (store, fetch, remove, tokenized link) with scan status.
- Email: the branded mailer with React Email templates.
- Notifications: write an in-app notification for a user.
- Audit: `moduleAudit(moduleId)` answers `audit(ctx, action, target, summary, metadata)`, with every action prefixed by the module id and the row written through `ctx.tx` when the caller passes its own transaction. Module actions stay out of the reader's fixed action filter, which lists only the core actions in `AUDIT_ACTIONS`. Built in Section 7.
- Datasets: `listDatasets(ctx)` answers the datasets of enabled modules whose permission the caller holds, without their `source`, and `queryDataset(ctx, { dataset, query })` runs one generic query over one of them as of the reporting date (`DEC-54`). `queryDatasetSeries(ctx, { series })` runs one query per series on its own dataset and permission and joins the answers on a shared `x` value, with a missing value `null` (R-7). Built in Section 7.
- Record route: `recordRoute(ctx, { dataset, id })` answers the `{ label, path }` page of the record behind one dataset row (R-11). It finds the dataset of an enabled module, resolves the row's `recordKey` type and id through the owning module's record-type resolver, and answers a route only when the resolver names a path and `can()` allows the path's permission on the record. The permission is the descriptor's own `permission`, or the owning module's `<id>:use` when it names none. Every miss answers `null`: an unknown or disabled dataset, a record the resolver does not find, a record with no path, or a caller the permission refuses. Built in Section 7.
- Events: `context.events.emit(tx, contract, payload)` with the transaction `withTransaction` handed the caller, or a savepoint opened inside it; any other transaction is refused. A module declares its handlers in `subscriptions` as `{ event, handler, name?, durable?, serializeBy? }`; `context.events.on(contract, handler)` registers a fast handler only. The payload is validated with the contract's schema at the emit. A subscription with no option is fast: it runs in process from the transaction's after-commit list, at most once and best effort, and only while its module is enabled. `durable: true` enqueues a pg-boss job inside the emitting transaction, so the job commits or rolls back with the data and is delivered at least once. `serializeBy` is durable too and runs one key at a time in creation order; `durable: false` beside it is refused. A durable or serialized subscription carries a required `name`, unique within its module, which its queue name derives from. Durable delivery is unordered unless serialized, so every handler is idempotent. Every envelope carries a `correlationId`: an emit inside a handler inherits the handled envelope's id, an emit inside a request inherits the request id the application set at the boundary (the forwarded `x-request-id`), and an emit outside both mints a fresh id. The id travels with the durable job, so a worker-side emit keeps it, and the log lines of one chain share it.
- Transactions: `withTransaction(ctx, fn)` runs `fn` in one transaction over the context's pool and hands it an after-commit registration. A module uses it when a write must commit or roll back together with the side effect it triggers. The registration `fn` receives targets the innermost savepoint's list: an entry registered through it inside `tx.transaction(...)` is discarded when that savepoint rolls back and runs when it is released, exactly like a fast handler emitted there. A fast in-process handler registered for after commit runs once the commit is durable, at most once and best effort: a crash between the commit and the dispatch loses it, with no retry. A handler that must not be lost uses the durable channel, which enqueues its pg-boss job inside the same transaction so the job commits or rolls back with the data (Section 1 item 9a, R-54, D-5). A module must not call `withTransaction` from inside `fn`; use `tx.transaction(...)` there for a savepoint.
- Capabilities: `context.capabilities.provide(moduleId, name, implementation)`, `context.capabilities.get(name)`, which returns the one provider or nothing and refuses a name two modules provide, and `context.capabilities.list(name)`, which answers every provider of an enabled module with its module id in registration order (R-13), with the interfaces declared in `packages/core/contracts`. `registerModuleRuntime(context, modules)` — called by the app bootstrap and by the worker with the same compiled list — registers every module's capability provisions, with its module id, and event subscriptions onto the context.
- Jobs: `enqueue(job, data, options)` and schedules.
- Streaming: the server-side proxy route pattern with a per-user send lease, for a module that relays an upstream event stream to the browser. The route mounts under `/api/m/<id>/...` and is authenticated by the user session and `can()`, unlike the Inbound endpoints point, which serves customer systems. First used by the solutions module (roadmap Section 4).
- Integrations: resolve a `tenant_integration` to configuration plus the live secret at call time.
- UI: the design-system primitives in `packages/ui`, the shell slots (page header, actions, empty state), tables, forms, and the record picker. The page header slot is `PageHeader` from `@genie/core/features/shell`: a page renders it inside its own `<main>` with its title, description, and actions, and inside the shell it hides the title where the top bar shows it and moves the actions into a phone bottom bar.
- Testing: the shared Vitest presets, Testcontainers Postgres, core factories, and generic database/context helpers. Each module owns its table factories and router/schema integration tests under its own `testing/` directory; the generator preserves that ownership. The app harness composes core and module helpers for the standing isolation test and the deployment-wide Playwright seed. Test imports obey the runtime layer boundaries.
  Modules with UI additionally own colocated documented Storybook stories, browser-safe fixtures, and applicable interaction tests, discovered by the development-only Storybook host without module-specific CI edits. These follow [the UI development workflow](ui-development.md) and supplement unit/integration/E2E tests. Fixture-driven permission states prove presentation, not authorization; headless modules do not need artificial UI stories.

## How modules talk to each other

Modules never import each other. Every conversation goes through core on one of four channels.

1. Events, the default. A module emits a named event with a zod-validated payload. An event only its own module handles is declared inside the module. An event that another module subscribes to is declared in `packages/core/contracts` with its name, schema, and version, and both sides import it from there (`DEC-42`). Any module subscribes by declaring the event in its `subscriptions`. Fast handlers run in process; slow or retryable ones run as pg-boss jobs. If the emitting module is disabled or not in the image, the event never fires.
2. Shared core records. A `file.id`, `user.id`, `group.id`, a notification, or an audit event handed over in an event payload. Both sides use the core service; neither reads the other's tables.
3. Capabilities, for the rare synchronous ask. Core declares a small named interface in `packages/core/contracts` (for example `DocumentSource`); a module registers as its provider; another module calls `context.capabilities.get('document-source')` and gets the provider or nothing. Both compile against core, never against each other, and a consumer must behave when the answer is nothing.
4. References by type and id. A record in one module remembers a record of another as a `<type>:<id>` text pair, labeled through the owning module's record-type resolver, never a foreign key.

Rules that keep the channels safe: `packages/core/contracts` imports only zod and TypeScript types, enforced by the oxlint `no-restricted-imports` rule, so a contract never pulls a module or a core service with it (`DEC-42`); event payload schemas are versioned and never change shape in place; a durable subscription's job is enqueued inside the emitting transaction and delivered at least once after it commits, a fast handler runs at most once after the commit, and events arrive in no guaranteed order, so every handler is idempotent and tolerates an older event after a newer one; a handler that cannot tolerate that subscribes with `serializeBy`, a function from the payload to a key such as the record id, and core then runs the jobs for one key one at a time in creation order — within one transaction in emission order, and across transactions in transaction-start order (pg-boss stamps `created_on` with `now()`, the transaction start, so two transactions that emit the same key are ordered by when each began, not by emission or commit time) — on a pg-boss queue with the `key_strict_fifo` policy and the key as `singletonKey`, which blocks every later job for a key while any job with that key is active, in retry, or failed), while jobs for different keys still run in parallel, and because a job that exhausts its retries on a serialized key blocks every later job for that key, every serialized queue declares a pg-boss dead-letter queue, the worker logs the move and the queue's `getBlockedKeys` at error level, and the operator runbook names the recovery: retry or delete the dead-letter job, and for a move pg-boss made on expiry rather than the worker, find it through the dead-letter queue and `getBlockedKeys`; a subscriber or capability consumer works when the other module is disabled or absent; every event carries a correlation id for tracing. Two modules that need each other's data synchronously and often are one module; merge them rather than widen a channel.

## What a module must not do

- Import another module. Cross-module needs go through core events or core records.
- Read or write another module's tables, or core tables other than `audit_event`, `notification`, and `file` through the services above.
- Check permissions anywhere except `can()`, or list records with record-scoped access without filtering on `scopesFor()` (`DEC-39`).
- Store a credential. Only a `tenant_integration.secret_ref`, or a key that an administrator typed, which core stores and resolves (`DEC-53`).
- Know who hosts the deployment, or which adapter stores files.
- Import a database driver or open a connection. The only database is `ctx.tenant.db` (`DEC-34`).
- Import from any `apps/*` package or assume the standard shell. Pages and navigation are components rendered by whichever app composes the module.
- Add a column to a core table. If a module needs data about a user or group, it keeps its own table keyed by `user.id` or `group.id`.

## How the contract grows

When a module needs a capability that is not in the first table, the change is made in core, documented here in the same pull request, and covered by a test in the placeholder module. Examples that are foreseeable and deliberately not built yet: full-text search across module records, a dashboard widget slot on a core Dashboard page (deferred by `DEC-49` until a second widget has requirements), per-user module preferences, and an outbound webhook subscription for customer systems. Each is a small addition to this list when a real module needs it. The navigation tree in the Navigation row was such an addition, made when the shell design needed a pinned rail and a category tree.
