# Module Contract

Status: draft for review, 2026-09-16. This is the single list of what a module may declare and what core provides. Customer modules are unknown in advance, so the rule is: a module uses these points and nothing else, and when a module needs something not on this list, the list is extended in core once, in the same change, so every later module gets it. A module never reaches around the contract.

Package names and folder basenames follow [Module package naming](repository-layout.md#module-package-naming). The module ID stays unprefixed: `contract-data` maps to `@genie/module-contract-data` in `packages/modules/contract-data/`. Package naming does not rename routes, permissions, entitlements, migration identities or selection IDs. Data-only metadata checks own package/folder/ID consistency; runtime declarations remain module-owned.

## What a module declares

Permission keys and default roles follow [Permission and system-role evolution](permission-evolution.md). Registration/seeding creates missing definitions, not new assignments or silent privilege expansions. Renames, retirement, and permission-affecting upgrades require the explicit migration and verification policy there.

### Migration declaration and authoring

The integrated Section 0 contract defers migration reads: `schema.migrations` is a function returning the module's migration metadata. Declare each journal entry's SQL file with a static `new URL(..., import.meta.url)` in the owning module, and call core's `migrationsFromJournal(journal, files)` inside that function. `moduleHistory` invokes it during bootstrap planning. Importing the declaration must not read SQL, connect to a database, or run migrations.

After changing the schema, run the module's drizzle-kit generation command, then add each new journal tag and its corresponding file URL to the declaration in the same change. Keep journal order and existing history semantics. A missing declared file fails when the history is read. The module continues to own its drizzle-kit folder and ledger table; this is not a second registry or an eager import-time migration read. The accepted example is `packages/modules/placeholder/src/schema.ts`.

Migration SQL is server-only. The standard app's build validates and removes generated public SQL duplicates while preserving server assets; authored public SQL fails the build. Keep migration declarations outside browser imports. Built-image acceptance must retain unavailable public SQL URLs, no migration contents in served assets/browser bundles, and correct real-database application with source/ledger hashes. Generator templates consume this contract, not the withdrawn raw/bytes-import alternatives. See the F2 decision and evidence in the S0-05 ticket.

### Content security policy provider

The enforced baseline (DEC-31, amended 2026-09-19) is `base-uri 'self'; object-src 'none'; frame-ancestors 'none'; frame-src 'none'`. On viewer documents core replaces only `frame-src` with validated owning-module origins. The core file download route sends the core `DOWNLOAD_POLICY` instead of the baseline (DEC-31, amended 2026-10-26); a module cannot change either. The app emits exactly one final enforced policy, not an additional deny-frames policy. No `default-src`, `script-src`, `style-src` or nonce wiring is required; strict script/style CSP and report-only evaluation are deferred. This removes no authorization, sandboxing, safe-rendering or tenant-isolation requirement. It does not constrain other resource types or force every page to render dynamically. Remote sites' own embedding restrictions still apply.

The provider is server-only and returns HTTPS origins, not full URLs, wildcard patterns, CSP keywords, or header fragments. An omitted provider or an empty result contributes no origins. It receives the deployment's `TenantContext`, never opens its own connection, and never reads another module's tables. The result is deployment-wide frame policy metadata, not a grant to view a record; page and record authorization remain behind `can()` and `scopesFor()`.

Core validates and deduplicates the returned origins before the app composes `frame-src`. Invalid contributions or provider failures must never fall back to a wildcard or the broad `https:` source; the response must not permit frames from a failed contribution. Core owns policy serialization, and modules cannot replace other CSP directives. The provider runs only for iframe-viewer document requests, so a change in its backing records is reflected on the next full viewer document response; a document already open retains its existing policy until reloaded.

Scope confirmed during the Spec 0 review: ordinary pages, API/oRPC calls, chat streams, health checks, static assets, and background prefetch/RSC requests must perform no frame-origin lookup. The app's server-owned route mapping identifies iframe viewer documents and their owning module; only that included module's provider is invoked. Entering an iframe viewer uses a full document navigation, including from the client-side shell, so its response installs the viewer policy before the iframe renders. Broader dynamic origin-policy coverage is deferred until a customer requirement justifies it. Ordinary security headers remain in place everywhere; the narrowed scope concerns database-backed iframe-origin computation only.

The placeholder supplies one fixed HTTPS origin in Section 0. A generated module includes a typed empty provider that contributes nothing until the module needs frames. Contract tests cover omission, empty output, duplicate origins, invalid values, and provider failure. The app's response-generation lifecycle and coverage are specified in the security-header requirements of the foundation specification.

## Category assignment boundary

Accepted 2026-09-19 (DEC-51 addendum). One Categories page assigns both whole modules and module records. Its core entry permission is `core:settings:manage`; providers additionally enforce their own record-management permission on reads and writes (Solutions uses `solutions:admin`). Core dispatches through the compiled registry, never imports module internals or accesses module tables. `listAssignable` returns authorized module/record identity, label and current category, not secrets or unrelated internal data.

Each write targets one record and a core category id or no category. Validate the category through core; recheck caller, tenant, module availability and record authorization at write time; audit successful changes in the owning module. Multi-row interactions report per-row outcomes and support retry, not a cross-module transaction. Placement never grants access. Disabled compiled modules retain record placement but contribute no editable record rows; excluded modules contribute nothing. Core placement of whole modules with static workspace entries remains available when disabled. Do not fall back to cached record rows or direct table access. Category summary counts remain whole-module counts only. Deletion touches no module table; missing category ids render ungrouped.

Section 0 declares/tests this optional interface with a synthetic placeholder without implementing runtime or broadening the authorization stub. Section 3 provides the common page/dispatch and core placement; Section 4 supplies Solutions' provider. Exact transport names are implementation choices, not new prescribed endpoints or tables.

## Settings discovery and authorization

Accepted 2026-09-19. Central settings reads, writes, section navigation and search require `core:settings:manage`. A section's optional additional permission is an AND restriction, never a substitute. Module administration alone does not grant central Settings access. Filter unauthorized metadata before returning it to the browser; direct links and saves enforce the same rule server-side.

Fuzzy search uses authorized section/field names, descriptions and keywords only, never saved values or secrets. Results open the section and focus the field or section heading. Stable ids support links; stale, absent and forbidden targets fail safely without disclosing hidden metadata. This adds neither cross-record search nor a sixth field kind/form engine.

Compiled disabled modules with a schema remain configurable through this authorized core pre-enable path, independently of disabled module routes. Saving never enables a module or bypasses reintroduction review. Excluded modules and modules without schemas contribute no section/search entries. Section 0 declares/tests metadata and permission shapes; Section 3 implements navigation, search, authorization and independent section saves. Preserve edits on refusal and ask before navigation discards them.

## What core provides to a module

- Tenant context: one object with the database connection, settings, branding, entitlements, and file store, passed into every procedure, job, and page. It is the only way to reach any of them (`DEC-34`).
- oRPC base and the contract seam ([ADR 0011](../adr/0011-replace-trpc-with-orpc.md)): a module's `contract.ts` imports only zod and the browser-safe `@genie/core/rpc` entry (`oc`), and is published as its `./contract` export; its router comes from core's `implementModule(id, contract)`. `implementModule` builds the router against the module request context, attaches the entitlement gate (`ctx.tenant.entitlements.isEnabled(id)`) and then the session check on the root `implementer.use()`, and throws the catalogue `AppError` `module-disabled` (with the request id) when the entitlement is off, before any input is parsed. A module never imports `@orpc/*`: the oRPC helpers reach it only through `@genie/core/rpc`, whose entry file exports only browser-safe values (`oc` from `@orpc/contract`, `appErrorData`, and `datasetCursorSchema`, so a contract can take and answer the dataset cursor of `czjw.28`). `implementModule`, the conformance check, and the server-side caller `callProcedure` live beside that entry and are exported from the core root, never from `@genie/core/rpc`; tests call procedures through `callProcedure` instead of importing `@orpc/*`. ## How modules talk to each other

Modules never import each other. Every conversation goes through core on one of four channels.

1. Events, the default. A module emits a named event with a zod-validated payload. An event only its own module handles is declared inside the module. An event that another module subscribes to is declared in `packages/core/contracts` with its name, schema, and version, and both sides import it from there (`DEC-42`). Any module subscribes by declaring the event in its `subscriptions`. Fast handlers run in process; slow or retryable ones run as pg-boss jobs. If the emitting module is disabled or not in the image, the event never fires.
2. Shared core records. A `file.id`, `user.id`, `group.id`, a notification, or an audit event handed over in an event payload. Both sides use the core service; neither reads the other's tables.
3. Capabilities, for the rare synchronous ask. Core declares a small named interface in `packages/core/contracts` (for example `DocumentSource`); a module registers as its provider; another module calls `context.capabilities.get('document-source')` and gets the provider or nothing. Both compile against core, never against each other, and a consumer must behave when the answer is nothing.
4. References by type and id. A record in one module remembers a record of another as a `<type>:<id>` text pair, labeled through the owning module's record-type resolver, never a foreign key.

Rules that keep the channels safe: `packages/core/contracts` imports only zod and TypeScript types, enforced by the oxlint `no-restricted-imports` rule, so a contract never pulls a module or a core service with it (`DEC-42`); event payload schemas are versioned and never change shape in place; a durable subscription's job is enqueued inside the emitting transaction and delivered at least once after it commits, a fast handler runs at most once after the commit, and events arrive in no guaranteed order, so every handler is idempotent and tolerates an older event after a newer one; a handler that cannot tolerate that subscribes with `serializeBy`, a function from the payload to a key such as the record id, and core then runs the jobs for one key one at a time in creation order — within one transaction in emission order, and across transactions in transaction-start order (pg-boss stamps `created_on` with `now()`, the transaction start, so two transactions that emit the same key are ordered by when each began, not by emission or commit time) — on a pg-boss queue with the `key_strict_fifo` policy and the key as `singletonKey`, which blocks every later job for a key while any job with that key is active, in retry, or failed), while jobs for different keys still run in parallel, and because a job that exhausts its retries on a serialized key blocks every later job for that key, every serialized queue declares a pg-boss dead-letter queue, the worker logs the move and the queue's `getBlockedKeys` at error level, and the operator runbook names the recovery: retry or delete the dead-letter job, and for a move pg-boss made on expiry rather than the worker, find it through the dead-letter queue and `getBlockedKeys`; a subscriber or capability consumer works when the other module is disabled or absent; every event carries a correlation id for tracing. Two modules that need each other's data synchronously and often are one module; merge them rather than widen a channel.

## What a module must not do

- Import another module. Cross-module needs go through core events or core records.
- Read or write another module's tables, or core tables other than `audit_event`, `notification`, and `file` through the services above.
- Check permissions anywhere except `can()`, or list records with record-scoped access without filtering on `scopesFor()` (`DEC-39`).
- Store a credential. Only a `tenant_integration.secret_ref`, or a key that an administrator typed, which core stores and resolves (`DEC-53`).
- Build a language model or call a model provider other than through `modelFor` (`DEC-55`).
- Know who hosts the deployment, or which adapter stores files.
- Import a database driver or open a connection. The only database is `ctx.tenant.db` (`DEC-34`).
- Import from any `apps/*` package or assume the standard shell. Pages and navigation are components rendered by whichever app composes the module.
- Add a column to a core table. If a module needs data about a user or group, it keeps its own table keyed by `user.id` or `group.id`.

## How the contract grows

When a module needs a capability that is not in the first table, the change is made in core, documented here in the same pull request, and covered by a test in the placeholder module. Examples that are foreseeable and deliberately not built yet: full-text search across module records, a dashboard widget slot on a core Dashboard page (deferred by `DEC-49` until a second widget has requirements), per-user module preferences, and an outbound webhook subscription for customer systems. Each is a small addition to this list when a real module needs it. The navigation tree in the Navigation row was such an addition, made when the shell design needed a pinned rail and a category tree.
