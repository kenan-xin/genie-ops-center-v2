## 1. The design is wrong, not the document

**1.1 Resolved by ADR 0007 on 2026-09-17 (section 3 item 3): one pool per deployment against one database.** Original finding: The connection pool math does not work. One pool per active tenant, two replicas, and the node-postgres default of ten connections exhausts a default-tuned Postgres at about ten active tenants, not fifty. At two hundred tenants the pool size falls to one or two, which serialises every request for that tenant. PgBouncer is named as the upgrade path (`core/roadmap.md:48`), but its constraints are free to write against now and repo-wide to retrofit later: no session state on the request path, no session advisory locks, migrations on a direct connection. Make PgBouncer the design. Separately, the cache has no eviction contract; ending a pool with checked-out clients kills in-flight queries.

**1.2 Decided on 2026-09-17 as DEC-39 (section 3 item 4): `scopesFor()` beside `can()`.** Original finding: `can()` cannot filter a list. It is a predicate over one resource (`architecture/data-shape.md:66`), and the module contract forbids checking permissions anywhere else (`architecture/module-contract.md:55`). A list screen with record-scoped grants then has two options, both wrong: evaluate the predicate per row after fetching everything, which makes `LIMIT` return the wrong page, or hand-roll the scope query inside the module, which the contract bans. Add the filter counterpart to the seam now: `scopesFor(user, permission)` returning either all or a list of ids. One function today, every list query and test later.

**1.3 Resolved by ADR 0007 on 2026-09-17 (section 3 item 2): a waiting replica serves after the other finishes, and no customer is suspended.** Original finding: A normal rolling deploy suspends healthy tenants. Both replicas run the migrator from the serving entrypoint (`core/roadmap.md:26`). The second replica blocks on each per-database advisory lock, times out after the stated 120 seconds, and suspends a tenant whose migration is succeeding on the other replica. Lock contention and migration failure are the same outcome in the current rule. Move the migrator to a one-shot release job; let the serving container verify the schema version and show a maintenance page for a tenant that is behind. A lock-wait timeout must retry and verify, never suspend.

**1.4 Resolved by ADR 0007 and `DEC-34` on 2026-09-17: one process serves one customer, every read goes through the one `TenantContext`, and the two-context isolation test stands (section 3 item 5).** Original finding: Nothing structurally prevents a query hitting the wrong tenant. Dropping `tenant_id` (`CLAUDE.md:31`) means a mis-routed query returns another tenant's rows rather than none. The replacement guarantee is ambient context, which the App Router breaks in three ways: middleware runs in a different runtime and cannot share async-local storage, `cache()` memoises on its argument list so a tenant-free cache key leaks across tenants inside one process, and a module-level database singleton is the most likely implementation of "core provides the connection". Three cheap layers fix it: thread an explicit tenant-branded handle so a query that cannot name its tenant does not compile, create a per-tenant Postgres role at provisioning so a mis-routed query fails at the server, and lint against cache keys without a tenant. The standing isolation test must also run both tenants through one warm process.

**1.5 Decided on 2026-09-17 as DEC-44: 15 MB on the `postgres` adapter, `FILE_MAX_BYTES` raised only with `s3`, blob column on external storage, no byte quota.** Original finding: files at 50 MB in Postgres will exhaust the container. There is no streaming path for a large `bytea` field in node-postgres: a download materialises the whole value as a buffer, and an upload is sent hex-encoded, so peak heap approaches four to five times the file size. Two or three concurrent 50 MB uploads exhaust a one-gigabyte container, and any authenticated person can trigger it. A 50 MB upload on a slow uplink also holds a pool connection for tens of seconds, which starves that tenant under the reduced pool size from 1.1. The justification given in DEC-20 (logos are kilobytes, document volume is low) argues for a 5 to 10 MB limit; set it there, require the `s3` adapter for any tenant entitled to a document-bearing module, add a per-tenant byte quota, and set the blob column to external storage in the first migration.

**1.6 Decided on 2026-09-17 as DEC-40: no custom theme. Local-account tenants get Keycloak's built-in credential emails with the realm display name. Branding through realm localization overrides stays the documented upgrade path.** Original finding: DEC-11 and `core/roadmap.md:96` write six values into realm attributes so the credential emails match the tenant's branding, and item 6a describes "one custom theme in `deploy/`" reading them. The FreeMarker email context is a fixed attribute map; adding values requires a custom `EmailTemplateProvider` packaged as a Java jar, deployed with Keycloak and re-verified on every Keycloak upgrade. That artefact is in no document. Either accept it and put it in the repository layout, the roadmap and the tech stack, or drop per-tenant branding from the three credential emails and keep Keycloak's own template with the realm display name.

**1.7 Fixed on 2026-09-17: every document, the sequence diagram, and the tech stack row now use `/api/auth/callback/keycloak`, with `signIn.social` and no client plugin, against Better Auth 1.7.** Original finding: the Better Auth callback path is wrong and gets baked into every realm. The documents pin `/api/auth/oauth2/callback/keycloak` in three places. The generic OAuth plugin moved to the core callback route in the release after the pinned line, so that URL is dead on a current install, and it is also written into the realm template at provisioning. Target the current release, use `/api/auth/callback/keycloak`, and note that the sign-in call and the client plugin changed names in the same release.

**1.8 Decided on 2026-09-17 as DEC-41: an absent claim keeps the previous memberships and writes an audit event, a present claim replaces them. No shrinkage alert and no guard inside the sync; the runbook asks the customer to emit assigned groups only.** Original finding: a missing groups claim can lock a tenant out of its own administration. Identity-provider memberships are replaced on every sign-in from the token's claim (`architecture/data-shape.md:56`). Microsoft Entra omits the claim entirely above roughly two hundred groups and sends an overage indicator instead, and any mapper misconfiguration does the same. Every role held through a group then disappears at the next sign-in. If a customer grants Tenant administrator to a directory group, the last-administrator guard never fires, because it sits on the admin-console path and not on the sign-in sync. Treat an absent claim as unknown and keep the previous memberships, replace only on a present claim, alert on a large shrinkage, and run the last-administrator guard inside the sync.

**1.9 Settled on 2026-09-17 in `chat-proxy.md`: a 30 second lease extended by a throttled heartbeat on every upstream event. The 120 second total cap and the total byte and event caps are removed, because a workflow can run for hours; the no-data timeout is `OPEN-S1` in the solutions module.** Original finding: the chat proxy lease is shorter than its own stream cap. The lease lives tens of seconds (`modules/solutions/chat-proxy.md:28`) while a stream may legitimately run to the 120-second total cap. A second send then acquires the lease mid-stream and two streams write the same conversation handle. Lengthening the lease past the cap blocks a user for two minutes after a hard crash. Heartbeat the lease instead: short life, extended while bytes flow.

## 2. Contradictions that will misdirect the first implementer

**2.1** Fixed on 2026-09-17: `CLAUDE.md` now states the `FileStorage` invariant with the database adapter as the default (`DEC-20`). The design repository's copy is outside this repository and is corrected there. Original finding: `CLAUDE.md:37` states "Files live in object storage, never in a database" while DEC-20 and `architecture/data-shape.md:86` store bytes in `file_blob`. The agent-facing file is read first. The design repository repeats the same wrong rule in its data shape.

**2.2** Fixed on 2026-09-17: the environment contract names the per-realm `genie-admin` client with rights in this realm only, and realm creation uses a one-run bootstrap credential (`DEC-37`). Original finding: the Keycloak admin credential is deployment-wide in `architecture/environment-contract.md:13` and per-realm in `architecture/data-shape.md:22`. The deployment-wide reading gives one compromised secret user-management rights in every tenant realm, which is the containment that realm-per-tenant was bought for. Use the per-realm client for everything except realm creation, and cache admin tokens per realm.

**2.3** Fixed on 2026-09-17: Tenant Settings is Section 3 item 10, and the `notification` table moved to Section 2 item 8 where the first write happens. Original finding: Tenant Settings is a fully designed screen, and DEC-28 says it is designed and implemented in Section 3, but Section 3 has no such work item and no roadmap section owns `tenant_settings`. Section 2 also writes an in-app notification to a table that Section 3 creates.

**Update 2026-09-17, after ADR 0007.** Every customer now runs its own deployment from its own image, so the shared multi-tenant process is gone. That resolves defects 1 (pool arithmetic), 3 (migrate-then-suspend), and 4 (cross-tenant query risk), concerns M2, M4, M10, and M12, the per-tenant key derivation in M1, and items 2, 3, 5 (the per-tenant parts), 7, and 8 below. DEC-34 keeps a return to many tenants in one process a bounded change. The remaining defects and items stand.
